# 前端工作流重构设计 v1

> 配套文档：`评估框架演进设计_v1.md`（数据层 / 接口 / 黄金集 CRUD 的总体设计）。
> 本文专注**前端**：把现在零散的页面（看板 / 测试集 / 黄金集 / 检索 / 对话）重排成一条**线性四步引导流**。
> 写在实现之前，动工时对照本文；与代码冲突以代码为准并回头更新。

---

## 0. 用户定义的工作流（一切设计的根）

```
① 上传原始文件
        ↓
② 大模型据文件生成黄金集（可填数量、可多选题型）
        ↓
③ 在 ①② 都有的前提下，批量从数据库查出每题的"结果证据包"（存库 + 展示）
        ↓
④ 据 ①②③ 生成最终评估报告
```

特点：**强顺序依赖**。后一步必须前一步有产出才能开始。所以前端主线就该是一个"步骤条 + 逐步解锁"的向导，而不是让用户在五个平级菜单间自己找路。

---

## 1. 总体信息架构

把页面分成两类：**一条主线（向导）** + **几个资产管理页（随时回看/维护）**。

```
顶部：项目选择器（沿用现有 #projSelect）

侧栏导航：
  ▶ 评估流程            —— 主线向导（四步），核心入口
  ─────────────
  · 黄金集库            —— 跨测试集的黄金记录管理（增改删，详见演进设计 v1 修改点2）
  · 评估报告            —— 历次 run 列表 / 指标 / 报告（读 run_summaries）
  · 看板总览            —— 项目健康度、各测试集最近得分
  · 对话试问            —— 保留
```

> 旧页面归属：
> - `测试集管理` + `黄金标注` + `检索评估` → 合并进【评估流程】向导的对应步骤；
> - `黄金标注库（只读表）` → 升级为【黄金集库】可编辑页；
> - `看板`、`对话试问` → 保留。

## 2. 【评估流程】向导：总体布局

一个页面，顶部一个**步骤条（Stepper）**，下面是当前步骤的工作区。每个测试集（suite）= 一次完整流程实例，进度存服务端，**刷新/换设备/跑一半都能恢复**。

```
┌───────────────────────────────────────────────────────────────┐
│  ①上传文件 ──●── ②生成黄金集 ──○── ③取证据包 ──○── ④生成报告      │   ← Stepper
│  （已完成）       （进行中）        （未解锁）      （未解锁）      │
├───────────────────────────────────────────────────────────────┤
│                                                                 │
│                   [ 当前步骤的工作区 ]                            │
│                                                                 │
├───────────────────────────────────────────────────────────────┤
│            [上一步]                         [下一步 / 完成]        │
└───────────────────────────────────────────────────────────────┘
```

**步骤解锁规则（前端门禁）：**
| 步骤 | 解锁条件 |
|---|---|
| ① 上传文件 | 选了项目即可 |
| ② 生成黄金集 | 该项目下已有 ≥1 个文档 |
| ③ 取证据包 | 当前 suite 已有 ≥1 道题且黄金集已确认（至少部分） |
| ④ 生成报告 | 当前 suite 已有 ≥1 题取到证据包 |

> 未解锁步骤在 Stepper 上置灰，点了给提示"请先完成上一步"。允许回看已完成步骤。

## 3. 四步详细设计

### 步骤 ① 上传原始文件

**职责**：把原始资料喂进项目，作为出题/黄金集的素材。

**界面**
- 拖拽 / 选择文件上传区（支持现有解析的格式）。
- 已上传文档列表：文件名 · 字数 · 章节数 · 上传时间，可多选（决定下一步用哪些文档出题）。

**调用接口**（已有）
- `POST /api/v1/projects/{pid}/documents`（multipart）
- `GET  /api/v1/projects/{pid}/documents`

**状态/落库**：文档存 `documents` 表。本步"完成"= 至少一个文档。

**恢复**：进页面读 `GET .../documents`，有则① 显示已完成。

---

### 步骤 ② 大模型生成黄金集（可填数量、可多选题型）

**职责**：基于①选中的文档，让大模型生成"问题 + 黄金标准（标准答案/关键点/应命中证据）"，人工可改可确认。这一步同时产出**问题**和**评估标准**。

**界面**
```
来源文档：[√ APN配置说明.md] [√ 网络搬迁最佳实践.chm] ...   （来自步骤①，多选）

题型（多选）：
  [√] 事实型   [√] 操作型   [ ] 推理型   [ ] 对比型   [ ] 排错型 ...

数量：  每种题型 [ 3 ] 道      （或：总数 [ 12 ] 道）

           [ 生成黄金集 ]   ← 调大模型，期间显示进度

────────────── 生成结果（草稿，待确认） ──────────────
□ 全选  [批量确认]
┌─ 问题1  [事实型] [草稿]                                    [编辑][确认]
│   标准答案：默认 APN 为 cmnet……
│   关键点：cmnet / 超时30秒
│   应命中证据：默认 APN 为 cmnet，连接超时阈值为 30 秒。
├─ 问题2  [操作型] [已确认] ……
```

**交互要点**
- 题型为**多选 chip**；数量为**可填输入框**（"每类 N 道"或"总数 N 道"，二选一模式）。
- 生成后每道题是一张可展开卡片，显示模型拟的黄金标准，状态 `草稿`。
- 单条【编辑】→ 改答案/关键点/证据/实体/难度/类型 → 保存；【确认】→ 状态变 `已确认`。
- 支持【批量确认】、单条【删除】、手动【新增一题】。
- **评估只采用"已确认"的黄金标准**（草稿不参与打分）。

**调用接口**
- 生成（已有，需让其顺带产出黄金草稿）：`POST /api/v1/projects/{pid}/suites:generate {document_ids, types[], per_type}`
  - 现状：已能按题型+每类数量出题并填 key_points。
  - 需补：生成时把"标准答案/证据"也作为**黄金草稿**写入（对齐演进设计 v1：`GoldRecord.status='draft'`、`source_kind='llm_generated'`）。
- 编辑/确认/删除黄金（演进设计 v1 修改点2）：
  - `PUT /api/v1/gold/{fingerprint}`、`POST /api/v1/gold/{fingerprint}:confirm`、`DELETE /api/v1/gold/{fingerprint}`
  - 用例侧回填仍可用 `PUT /api/v1/suites/{sid}/cases/{cid}/gold`
- 标注进度（已有）：`GET /api/v1/suites/{sid}/gold/progress`

**状态/落库**：问题存 `suites`，黄金标准存 `gold` + 回填用例。本步"完成"= 至少一题黄金 `已确认`。

**恢复**：进页面若当前 suite 已存在，读 cases + gold/progress 还原列表与确认状态。

---

### 步骤 ③ 批量获取"结果证据包"

**职责**：对②里的每道题，去**我们的知识库数据库**查一遍，把检索到的片段（证据包）存库并展示。这是**回答/检索结果**层。

**界面**
```
证据来源：(•) serving 真实查询日志   ( ) Claude 自动检索(MCP)     ← 取证方式
检索器名：[ serving ]    domain（可空）：[        ]

      [ 批量取证据包 ]   ← 逐题进行，SSE 实时进度

进度：第 5/12 题：默认 APN 是…   （成功 4 · 失败 0 · 跳过 1）

────────────── 每题证据包 ──────────────
┌─ 问题1  [事实型]                                  已取 2 条
│   #1  默认 APN 为 cmnet，连接超时阈值为 30 秒。   出处：APN.md
│   #2  若连接失败，先检查 APN 拼写与超时配置。     出处：APN.md
├─ 问题2 …   未匹配 → [相似候选，确认后拉取]
```

**交互要点**
- 顶部选"取证方式"：① serving 真实日志（默认）② Claude 自动检索（MCP，复用已做的 SSE 跑批）。
- 【批量取证据包】走 SSE，**实时刷新**当前在取哪题、成功/失败/跳过计数（复用步骤化进度组件）。
- 单题未精确命中 → 展示相似候选，人工【确认拉取】。
- 已取的题展示证据条目（排名 + 文本 + 出处）。可单题【重取】。
- **跳过逻辑**：已有证据包的题默认跳过（断点续跑），可勾选"全部重取"。

**调用接口**
- serving 逐题（已有）：`POST /api/v1/suites/{sid}/cases/{cid}/retrieval:pull`
- Claude 自动检索批量（已有，SSE）：`GET /api/v1/suites/{sid}/agent:run/stream`
- 进度恢复（已有）：`GET /api/v1/suites/{sid}/retrieval/progress`
- **需补**：serving 的"批量取证据包 + SSE 进度"端点（现在前端是逐题循环 `pullAllCases`，建议比照 agent SSE 加一个 `GET /api/v1/suites/{sid}/retrieval:pull/stream`，统一实时进度体验）。

**状态/落库**：证据包存 `retrieval_sets`。本步"完成"= 至少一题有证据。

**恢复**：进页面读 `retrieval/progress`，把已取证据包还原展示。

---

### 步骤 ④ 生成最终评估报告

**职责**：拿①②③（文档 / 黄金标准 / 证据包）跑评估，出指标和报告。

**界面**
```
评估范围：(•) 仅已确认黄金且有证据的题   ( ) 全部已取证据的题
评估标准（只读快照）：K=[1,3,5,10] · 通过线 Recall≥0.5 / rankFirst≤3 / ctxRecall≥0.8 · 权重 …

      [ 生成评估报告 ]   ← 逐题大模型判相关度(0–3) + 聚合，SSE 进度

────────────── 结果 ──────────────
[ NDCG@10  72% ] [ Recall@10 65% ] [ HitRate 80% ] [ MRR 0.71 ] [ KB综合分 68 ]
诊断：高噪声 2 题 · 未命中 1 题 · 难度分层 …
逐题可展开：证据 → 每条相关度 → judge 理由 → token   （评估过程可追溯）

[ ↗ 打开 HTML 报告 ]   [ ↗ Markdown ]   [ 保存到报告历史 ]
```

**交互要点**
- 评估前展示**评估标准快照**（阈值/权重/K），让用户知道这次按什么尺子量（"评估标准透明"）。
- 逐题判定走 SSE 实时进度。
- 出指标卡 + 诊断桶 + 难度分层；逐题可展开看"证据 → 相关度 → 理由 → token"，落实**评估过程可追溯**。
- 报告自动入【评估报告】历史（写 `run_summaries`）。

**调用接口**
- 评估（已有）：`POST /api/v1/suites/{sid}/retrieval:evaluate {k_values, only_annotated}` 或逐题 `retrieval:judge` + `retrieval:report`
- 报告（已有）：`GET /api/v1/retrieval-runs/{rid}/report?format=html|md`
- **需补**：评估时写一条 `run_summaries`（演进设计 v1 修改点1），供报告历史/看板列出。

**状态/落库**：明细 `retrieval_runs`，摘要 `run_summaries`。本步"完成"= 出过一次报告。

## 4. 进度状态机与恢复

每个 suite 维护一个流程状态，前端进入向导时一次性拉取并定位到该停的步骤。

```
状态：DOC_READY → GOLD_DRAFT → GOLD_CONFIRMED → EVIDENCE_READY → REPORTED
                                  （可回退/补充任意已完成步骤）
```

**恢复来源（尽量复用已有接口，缺口见第5节）**：
- 文档：`GET /projects/{pid}/documents`
- 题 + 黄金：`GET /suites/{sid}` + `GET /suites/{sid}/gold/progress`
- 证据包：`GET /suites/{sid}/retrieval/progress`
- 报告：`GET /suites/{sid}/runs`（新增）

> 建议后端补一个聚合恢复接口 `GET /api/v1/suites/{sid}/state`（演进设计 v1 已列），一次返回四步完成度，省得前端拼四个请求。

| 优先 | 端点/能力 | 用途 | 状态 |
|---|---|---|---|
| 高 | `GET /projects/{pid}/suites` | 测试集列表（废弃 localStorage 记账） | 新增 |

> 已具备、直接复用：文档上传、`suites:generate`、逐题 `retrieval:pull`、`agent:run/stream`(SSE)、`retrieval:evaluate/judge/report`、报告渲染、`retrieval/progress`、`gold/progress`。

## 6. 前端落地顺序（不一把梭）

1. **搭向导骨架**：Stepper 组件 + 四步容器 + 解锁门禁 + 路由 `#/flow`。先用现有接口把四步串起来跑通（黄金集生成先用现有 suites:generate 的 key_points 占位）。
2. **步骤②升级**：接入黄金草稿生成 + 编辑/确认 UI（依赖后端黄金 CRUD）。
3. **步骤③升级**：serving 批量取证 SSE，统一进度体验。
4. **服务端清单切换**：测试集/报告列表改读服务端，localStorage 退兜底。
5. **资产页**：黄金集库（可编辑）、评估报告（历史）独立页。
6. 视觉与交互打磨。

每步按"科学方法闭环"：定义→方案→写码→测试回归。

## 7. 待确认问题

1. 步骤②数量：用"每类题型 N 道"还是"总数 N 道"？（建议默认"每类 N 道"，与现有 `per_type` 对齐）
2. 步骤③默认取证方式：serving 真实日志 vs Claude 自动检索(MCP)？（建议默认 serving，更贴合"从我们数据库查出"）
3. 向导是否允许"跳步回看"（已完成步骤可改）？（建议允许，改了下游标记为需重跑）
4. 旧的独立"检索评估页"是直接下线并入向导，还是过渡期并存？（建议过渡期并存，稳定后下线）
