## 0. 北极星：把"一次性体检"变成"工作流驱动 + 资产沉淀 + 可追溯"

用户工作流（一切的脊柱，强顺序依赖）：

```
① 上传原始文件 → ② 大模型生成黄金集(可填数量/多选题型) → ③ 批量取数据库证据包 → ④ 生成评估报告
```

框架要管的 6 类对象：**黄金集 · 问题 · 回答(证据) · 评估标准 · 评估过程(可追溯) · 评估报告**。
核心病根：很多数据已落 SQLite，但没有"列出来"的接口，前端只能靠 localStorage 记账 → 评测跑完即弃、换设备就丢。

---

## 1. 已锁定的决策（原两文开放问题在此拍定）

| # | 问题 | 决策 |
|---|---|---|
| D1 | 黄金集生成的输入 | **以"文档自动出题 + 出黄金"为主**（贴合工作流①→②） |
| D2 | 数量怎么填 | **"每种题型 N 道"**，对齐现有 `per_type` |
| D3 | ③默认取证方式 | **默认 serving 真实日志**；Claude 自动检索(MCP) 作为可选 |
| D4 | 向导能否跳步回看 | **允许**回看/修改已完成步骤；改了上游 → 下游标记"需重跑" |
| D5 | 旧"检索评估页" | **过渡期并存**，向导稳定后下线 |
| D6 | 导航改造方式 | **渐进改造**，按 Phase 切，不一把梭 |
| D7 | run 跨次对比(diff) | **下期**，本期只做"列出历史 + 单次报告" |
| D8 | 评估深度(L2/忠实度/judge可信度…) | **本期不做**，待专题讨论后另立设计 |
| D9 | 评估只用哪种黄金 | **仅 `status='confirmed'`** 参与打分，草稿不参与 |

## 2. 全景：本期要交付什么

```
后端（eval-api / eval-llm / SQLite）
  ├─ 档案化：list_suites、run_summaries 表、列表/恢复接口
  ├─ 黄金集：GoldRecord 加 status/source_kind、直接 CRUD、生成顺带黄金草稿
  └─ 取证：serving 批量取证 + SSE（统一实时进度）

前端（eval-web SPA）
  ├─ 主线：四步向导（Stepper + 逐步解锁 + 刷新恢复）
  ├─ 资产页：黄金集库(可编辑)、评估报告(历史)、看板(读摘要)
  └─ 服务端清单替代 localStorage 记账（后者退为离线兜底）

不在本期：评估深度(D8)、跨次对比(D7)
```

## 3. 分阶段计划（每阶段独立可交付，按序推进）

> 每阶段都走"科学方法闭环"：定义→方案→写码→测试回归。每阶段末跑全量 `pytest` 绿灯方可进下一阶段。

### Phase 0 · 服务端档案化（地基，最高优先级）

**目标**：评测能累积、能恢复，localStorage 退居兜底。

**后端**
- `sqlite_store.py`：
  - 新增 `list_suites(project_id)`（`suites` 表已有 `project_id` 列，直接查）。
  - 新增 `run_summaries` 表（DDL 见演进设计 v1 §2.2）+ `save_run_summary` / `list_run_summaries(project_id|suite_id)` / `latest_run_summary(suite_id, layer)`。
- `app.py`：
  - `GET /api/v1/projects/{pid}/suites`
  - `GET /api/v1/projects/{pid}/runs`、`GET /api/v1/suites/{sid}/runs`
  - `GET /api/v1/suites/{sid}/state`（聚合：文档数 / 题数 / 黄金确认数 / 证据数 / 最近 run 状态 → 四步完成度）
  - 在 `judge` / `retrieval:evaluate` / `retrieval:report` 落库时**顺手写 `run_summaries`**（逐题流程：判一题写 `partial`，全判完 `done`）。

**前端**
- 测试集下拉、看板、报告列表改读上述接口；`kb_suites` / `kb_runsum` 仅作读取失败兜底。

**测试**：list/summary 接口往返；`/state` 在各阶段返回正确完成度；旧测试回归。
**验收**：换浏览器仍能看到测试集与历史评测；跑一半的逐题进度能恢复。

---

### Phase 1 · 黄金集资产化（CRUD + 草稿/确认 + 生成顺带黄金）

**目标**：黄金集可"生成→展示→改→确认→删"，评估只认已确认。

**后端**
- `shared/models.py`：`GoldRecord` 加 `source_kind: str = "manual"`、`status: str = "confirmed"`（读旧数据给默认值，无需迁移）。
- `app.py`：
  - `GET /api/v1/gold/{fingerprint}`、`PUT /api/v1/gold/{fingerprint}`、`DELETE /api/v1/gold/{fingerprint}`、`POST /api/v1/gold/{fingerprint}:confirm`
  - `suites:generate` 改造：生成题目时**同时产出黄金草稿**（`status='draft'`、`source_kind='llm_generated'`）并入 `gold` 表 + 回填用例。
  - 评估链路过滤：打分只取 `confirmed` 黄金（D9）。
- `eval_llm`：复用现有 LLM 客户端产出"标准答案/关键点/证据"（如需新 prompt，仅在 eval-llm 侧加，保持分层）。

**前端**
- 【黄金集库】页升级为可编辑：列表(问题/类型/证据数/状态/更新时间) + 筛选 status + 编辑面板 + 新建 + 删除 + 批量确认。

**测试**：CRUD 往返；generate 产出 draft；评估忽略 draft 只用 confirmed；旧测试回归。
**验收**：能在黄金集库里改一条并确认；草稿不影响评分。

---

### Phase 2 · 四步向导骨架（把流程串起来）

**目标**：用现有能力把①②③④串成一条向导跑通（端到端可用）。

**前端**（`eval_web/static`：`app.js` / `index.html` / `styles.css`）
- 新增路由 `#/flow` 与侧栏入口【评估流程】。
- Stepper 组件 + 四步容器 + **解锁门禁**（①选项目；②有文档；③有题且黄金已确认；④有证据包）。
- 进入向导调 `GET /suites/{sid}/state` 一次性定位到该停的步骤（刷新/换设备恢复）。
- 各步接线（复用为主）：
  - ① `documents` 上传/列表
  - ② `suites:generate`（D2 每类 N 道、题型多选）+ Phase 1 黄金编辑/确认
  - ③ 逐题 `retrieval:pull`（默认 serving，D3）/ 可选 `agent:run/stream`
  - ④ `retrieval:evaluate`/`report` + Phase 0 的 `run_summaries`
- D4：改了上游步骤 → 下游打"需重跑"标记。

**测试**：SPA 资源断言（`#/flow`、Stepper、各步关键调用串存在）；旧 SPA 断言回归。
**验收**：一个新项目能从上传一路点到出报告，刷新不丢进度。

---

### Phase 3 · 取证与评估体验统一（SSE + 标准透明 + 可追溯）

**目标**：③④都有实时进度，评估标准看得见，过程查得到。

**后端**
- `app.py` + `orchestrator.py`：新增 `GET /api/v1/suites/{sid}/retrieval:pull/stream`（serving 批量取证 + SSE，复用 agent SSE 事件格式 start/case_start/case_done/case_error/done）。

**前端**
- ③【取证据包】走 SSE 实时进度（与 agent 跑批同一进度组件）；未命中→相似候选确认；已取跳过/可重取。
- ④【生成报告】前展示**评估标准快照**（K / 通过线 / 权重）；出指标卡 + 诊断桶 + 难度分层；逐题可展开"证据→相关度→judge 理由→token"（评估过程可追溯）。

**测试**：serving 批量 SSE 事件序列与落库；标准快照取自 config；旧测试回归。
**验收**：③ 实时看到在取哪题；④ 能看到这次按什么尺子量、每题为何这么判。

---

### Phase 4 · 资产页打磨 + 旧页下线

**目标**：六类对象齐全、入口清晰，去掉历史包袱。

**前端**
- 【评估报告】历史页：读 `run_summaries` 列历次评测 → 打开 HTML/MD 报告。
- 【看板】读 `run_summaries` 展示各测试集最近得分/状态。
- 导航定稿（评估流程 / 黄金集库 / 评估报告 / 看板 / 对话试问）。
- D5：向导稳定后，下线旧"检索评估页"（或重定向到向导）。

**测试**：报告历史/看板读摘要正确；导航与路由回归。
**验收**：换设备打开能看到完整历史与报告；旧入口已收敛。

---

### Phase 5 · 评估深度（本期不做，占位）

待专题讨论后另立设计（L2 工具层 / 答案忠实度·grounding / judge 可信度 / 成本延迟门禁 / 失败归因）。详见演进设计 v1 §5。

## 4. 阶段依赖与顺序理由

```
Phase 0（档案地基）── 是 2/3/4 的前提（列表、恢复、run_summaries）
      └─ Phase 1（黄金集底座）── 是向导②的前提
              └─ Phase 2（向导骨架，端到端跑通）
                      └─ Phase 3（SSE/标准/追溯，体验升级）
                              └─ Phase 4（资产页 + 旧页下线）
                                      └─ Phase 5（评估深度，另立）
```

理由：先把"数据列得出来 + 恢复得回来"（0）和"黄金集改得动"（1）这两块地基打牢，向导（2）才有东西可串；体验（3）和收尾（4）在功能跑通后再加，风险最低。

## 6. 贯穿性约束（每阶段都要守）

- 兼容优先：新表/新字段"建表即建、读时给默认值"，**不写迁移脚本**（已是 SQLite 单后端）。
- 分层不破：模型能力留在 eval-llm，eval-api 只编排。
- 静态资源带版本号（`app.js?v=...`），发版即换，避免浏览器缓存旧 JS。
- 每阶段末全量 `pytest` 绿灯；前端关键接线进 SPA 断言。
- **不擅自提交 git**：每阶段完成后等用户确认再考虑提交。
