# 知识库评估框架 · 演进设计 v1

> 目的：把"一次性体检仪"演进为"评测资产沉淀 + 黄金集飞轮 + 全流程可追溯"的平台。
> 本文是实现前的设计稿，后续动工时对照本文。最终评估深度（方向三）暂留为开放讨论，不在本期定稿。

---

## 0. 一张图看懂：评估框架到底要管哪几样东西

用户心智里，一个知识库评估框架就管 6 类对象（本文一切设计都围绕它们）：

| 对象 | 含义 | 现状 | 缺口 |
|---|---|---|---|
| **黄金集** | 标准答案 / 关键点 / 应命中证据（评判依据） | 有 `gold` 表 + 指纹复用；但只能从用例侧写入，库页只读 | ❌ 不能直接增改删；❌ 无大模型生成；❌ 无独立编辑页 |
| **问题** | 测试集里的题（cases） | 有 `suites` 表 | ❌ 无服务端清单接口（前端 localStorage 记账） |
| **回答** | agent / serving 给出的答案（responses） | 有 `responses` 表 | ⚠️ 进度恢复不完整 |
| **评估标准** | 阈值、权重、打分规则、相关度 rubric | 散在 `ApiConfig` + 黄金证据里 | ⚠️ 不透明、不可视 |
| **评估过程（可追溯）** | 每题怎么被判的、判了几次、token、理由 | 有 `runs`/`retrieval_runs` 落库 | ❌ 无清单/无历史浏览，跑完即弃 |
| **评估结果报告** | 指标 + MD/HTML 报告 | 报告落磁盘，指标摘要存 localStorage | ❌ 报告/指标无服务端清单，换设备即丢 |

**核心病根：很多东西其实已经落进 SQLite 了，但没有"列出来"的接口，前端只能靠 localStorage 自己记账。** 本期主线就是把这些"列出来"，让评测变成可累积的资产。

## 2. 修改点 1：评测档案（Server-side Registry）

### 2.1 目标
1. suite 列表、run 指标都从服务端读，**废弃 localStorage 记账**（`kb_suites`/`kb_runsum` 降级为离线兜底缓存，不再是唯一真相）。
2. **跑到一半的结果能暂存、再进页面能恢复**（不用重头跑）。
3. 为将来"版本对比 / 趋势 / 回归门禁"打地基。

### 2.2 数据层改动（SQLite）
现有表基本够用，主要是**补查询能力**，外加一张"run 摘要"表方便看板/趋势聚合（避免每次反序列化整个 run）。

```sql
-- 新增：评测结果摘要（一次评估跑批 = 一行），看板/趋势/对比直接读这里
CREATE TABLE IF NOT EXISTS run_summaries (
    run_id      TEXT PRIMARY KEY,   -- 复用 runs / retrieval_runs 的 run_id
    project_id  TEXT,
    suite_id    TEXT,
    layer       TEXT,               -- 'retrieval' | 'response'（检索层 / 应用层）
    kind        TEXT,               -- 'perq' | 'batch' | 'live' 等
    created_at  TEXT,
    k           INTEGER,            -- 主 K（如 10）
    metrics_json TEXT NOT NULL,     -- 关键指标快照（ndcg/recall/hit/mrr/ctx_recall/kb_score/judged/total...）
    status      TEXT                -- 'partial' | 'done'（支持"未跑完暂存"）
);
CREATE INDEX IF NOT EXISTS ix_run_summaries_suite ON run_summaries(suite_id);
CREATE INDEX IF NOT EXISTS ix_run_summaries_project ON run_summaries(project_id);
```

> 说明：明细仍存在 `runs`/`retrieval_runs`（payload JSON）。`run_summaries` 只是"抽出来的封面"，让列表/趋势查询不必读大 payload。

`SqliteStore` 新增方法：
- `list_suites(project_id) -> list[TestSuite | SuiteSummary]`（按 `suites` 表，已有 `project_id` 列，直接查）
- `save_run_summary(summary)` / `list_run_summaries(project_id=None, suite_id=None)`
- `latest_run_summary(suite_id, layer)`（看板用）

### 2.3 API 改动
| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/v1/projects/{pid}/suites` | 列出项目下所有测试集（替代 localStorage `kb_suites`） |
| GET | `/api/v1/projects/{pid}/runs` | 列出项目下所有评测摘要（看板/历史） |
| GET | `/api/v1/suites/{sid}/runs` | 列出某测试集的历次评测（趋势/对比基础） |
| GET | `/api/v1/suites/{sid}/state` | **恢复用**：聚合该 suite 的应用层作答进度 + 检索逐题进度 + 最近 run 状态，一次性返回，前端进页面即恢复 |

> `judge` / `retrieval:evaluate` / `retrieval:report` 等现有出指标的端点，落库时**顺手写一条 `run_summaries`**（`status='done'`）。逐题流程在每题判定后可写 `status='partial'`，全部判完更新为 `done` —— 这就是"暂存未跑完"。

### 2.4 前端改动
- 测试集下拉、看板卡片从 `/projects/{pid}/suites` + `/projects/{pid}/runs` 读。
- 进入检索/应用层页面时调 `/suites/{sid}/state` 恢复（逐题进度现已有 `retrieval/progress`，本步是把"应用层作答进度 + 上次 run 状态"也纳入一次性恢复）。
- `kb_suites`/`kb_runsum` 保留为读取失败时的兜底，不再作为写入主路径。

## 3. 修改点 2：黄金集（生成 / 展示 / 修改）

### 3.1 现状
- `gold` 表（按 `fingerprint` 主键，跨 suite 复用）。
- 写入只有一条路：`PUT /suites/{sid}/cases/{cid}/gold`（先写用例，再同步黄金库）。
- 前端 `gold` 页 = 只读表格 + 逐用例标注，**不能直接编辑库里的记录，也没有大模型生成入口**。

### 3.2 目标
黄金集要能：**大模型生成草稿 → 独立页面展示 → 人工增 / 改 / 删 → 落库复用**。

### 3.3 数据层
`GoldRecord` 模型基本够用。建议补两个字段以支撑"草稿 → 确认"工作流和可追溯：
```
source_kind: str = "manual"     # manual | llm_generated | imported
status: str = "confirmed"       # draft（大模型生成待确认） | confirmed（人工确认）
```
> 评估时**只采用 `status='confirmed'` 的黄金证据**，草稿不参与打分，避免"机器生成未经人审"污染评判标准。

### 3.4 API 改动（黄金集直接 CRUD，不再只能从用例侧）
| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/v1/projects/{pid}/gold` | 列出黄金库（已有，补 status/source_kind 字段返回） |
| GET | `/api/v1/gold/{fingerprint}` | 取单条 |
| PUT | `/api/v1/gold/{fingerprint}` | **直接编辑**一条黄金记录（答案/关键点/证据/实体/难度/类型/备注） |
| DELETE | `/api/v1/gold/{fingerprint}` | 删除一条 |
| POST | `/api/v1/projects/{pid}/gold:generate` | **大模型生成黄金集草稿**：输入问题列表 / 文档，由 eval-llm 产出 expected_answer/key_points/evidence，落库为 `status='draft'` |
| POST | `/api/v1/gold/{fingerprint}:confirm` | 把草稿确认为 confirmed（可带人工修订） |

> 生成走现有 eval-llm 通道（新增一个 `/generate-gold` prompt 或复用出题/judge 的 LLM 客户端），保持"模型能力都在 eval-llm，eval-api 只编排"的分层不变。

### 3.5 前端：独立"黄金集"页（升级现有 gold 页）
- **库视图**：表格列出全部黄金记录（问题 / 类型 / 证据数 / 状态 draft|confirmed / 更新时间），支持筛选 status。
- **编辑**：点行 → 编辑面板（答案、关键点、证据、实体、难度、类型、备注），保存走 `PUT /gold/{fp}`。
- **新建**：手动新增一条。
- **大模型生成**：选文档 / 粘问题 → `gold:generate` → 草稿批量入库 → 列表里黄色"待确认" → 人工逐条改 + 确认。
- 保留"用例侧标注"入口（测试集里对某题标注，仍走原 `cases/{cid}/gold`），两条路写同一张 `gold` 表，按指纹合并。

## 4. 修改点 4：前端信息架构重构

### 4.1 原则
导航按"6 类对象 + 一条主流程"重排，让用户一眼知道"东西在哪、流程走到哪"。

### 4.2 建议导航（替代现有 dashboard/suites/gold/retrieval/chat）
```
看板总览        —— 项目健康度、各 suite 最近评测、趋势（读 run_summaries）
黄金集          —— 生成 / 展示 / 增改删（修改点 2）
测试集与问题    —— suite 列表（服务端）、题目浏览、导入/生成
回答与跑批      —— agent 自动跑批(SSE) / 上传回答 / 作答进度恢复
评估与追溯      —— 检索层 + 应用层评估；逐题相关度、判定理由、token（过程可追溯）
评估报告        —— 历次 run 列表、指标、MD/HTML 报告、（将来）版本对比
对话试问        —— 保留
```
> 不必一次推倒重来。落地顺序：先把"测试集/回答/报告"从 localStorage 切到服务端清单（修改点 1 的前端部分），再把黄金集页升级（修改点 2），最后调整导航分组与视觉。

### 4.3 "评估过程可追溯"具体要展示什么
- 每题：检索到的片段（带排名/出处）→ 每条的相关度 0–3 → judge 的理由文字 → 判定消耗 token。
- 每次 run：用了哪个黄金集版本、哪些阈值/权重（评估标准快照）、跑批耗时、失败题清单。
- 这些数据**现在大多已落在 `retrieval_runs` 的 payload 里**，缺的是把它"列出来 + 摊开看"的页面。

## 5. 修改点 3：评估深度（🟡 开放，待讨论，不在本期实现）

记录下来供后续专门讨论，先不动代码：

1. **L2 工具层**：MCP 工具选得对不对、参数对不对、多轮调用合不合理 —— 当前评得薄。
2. **答案忠实度 / grounding**：答案是否真的基于检索片段（防幻觉）、引用出处是否准确、该拒答的有没有乱答。
3. **Judge 可信度**：裁判与人工标注的吻合度、同题多跑的评分方差、模型升级后的"标准漂移"。
4. **成本 / 延迟门禁**：token、latency 已在收集，是否升为一等指标并纳入回归阈值。
5. **失败归因**：检索砸了到底是文档缺失 / 切分差 / embedding 弱 / query 改写偏 —— 从"给数字"到"给修复建议"。

> 待确认：上面哪几项优先？评估深度是先做"忠实度"还是先做"judge 可信度"？这决定下一份设计的主题。

## 7. 兼容与迁移注意

- `run_summaries`、`GoldRecord` 新字段都用"建表/读时给默认值"，老数据无需迁移（旧 gold 记录读出来 `status` 默认 `confirmed`、`source_kind` 默认 `manual`）。
- 已只剩 SQLite 单后端，新表跟着 `_SCHEMA` 一起 `CREATE TABLE IF NOT EXISTS`，启动即建，无脚本。
- 前端 localStorage 的 `kb_suites`/`kb_runsum` 不删，作为服务端读取失败时的离线兜底，平滑过渡。
