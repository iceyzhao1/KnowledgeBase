## 0. 这是什么 / 你能得到什么

runtime_eval 是一把**尺子**：量化"被测问答 Agent（copilot 形态）在运行态的真实
回答到底对不对、快不快、贵不贵"。它**与被测服务解耦**——被测 Agent 是 Java 还是
Python、本地还是远程，都不影响本框架。

你最终会得到一份报告，包含：

- **按问题类型区分的准确率**（事实/概念/操作/约束/故障/导航各一档）；
- **查询时长**（均值 / P50 / P95 / 最大）；
- **token 消耗**（被测 Agent 自身 + 框架出题裁判成本，分开统计）；
- 可选的**检索层 IR 指标**（HitRate / Recall / MRR / NDCG / Context Precision/Recall）。

三个服务，依赖方向 `前端 → eval-api → eval-llm`：

| 服务 | 干什么 | 端口 |
|------|--------|------|
| **eval-llm** | 大模型服务：出题 + 裁判打分，封装密钥/Provider | 8801 |
| **eval-api** | 后端编排 + 持久化，并托管前端页面 | 8800 |
| **eval-web** | 浏览器前端（由 eval-api 在 `/` 托管，无需单独启动） | — |

## 1. 五分钟跑通（mock，零配置）

`mock` provider 不需要网络、不需要任何 Key，用确定性假数据把全链路跑通，先验证环境。

### 1.1 装依赖（一次性）

**必须 Python ≥ 3.10**（本机默认 `py` 可能是 3.9，请显式 `py -3.10`）。

```bash
pip install -r requirements.txt                 # 仓库根：核心依赖
pip install -r runtime_eval/requirements.txt    # 本框架增量（python-multipart、pyyaml 等）
```

### 1.2 配 .env

在 `runtime_eval/` 目录下，把示例复制成 `.env`：

```powershell
# Windows PowerShell
Copy-Item .env.example .env
```
```bash
# bash
cp .env.example .env
```

默认 `EVAL_LLM_PROVIDER=mock`，无需再改。

### 1.3 起两个服务

开**两个终端**，都 `cd` 到仓库根的 `runtime_eval/` 目录：

```bash
# 终端 1：大模型服务（先起）
py -3.10 -m runtime_eval.eval_llm --host 127.0.0.1 --port 8801

# 终端 2：后端 + 前端
py -3.10 -m runtime_eval.eval_api --host 127.0.0.1 --port 8800
```

### 1.4 打开前端

浏览器访问 <http://127.0.0.1:8800> 。按 [§3](#3-完整使用流程生成层回答质量) 的流程点一遍，
mock 会产出假题、假分，全链路能走通即说明环境 OK。

> ✅ 跑通后，再去 [§2](#2-接上真实大模型推荐-claude--p) 换成真实大模型。

## 2. 接上真实大模型（推荐 claude -p）

**只改 `runtime_eval/.env` 里 eval-llm 的配置，代码零改动，重启 eval-llm 即生效。**
eval-api 完全不用动。

### 方式一（推荐）：本机 Claude Code CLI（`claude -p`）

复用你**已安装并登录好**的 `claude` 命令做出题/裁判，**本仓库不需要配置任何 API Key**。

前置：`claude` 已在 PATH 上（命令行能直接 `claude` 启动即可；Windows 会自动识别
`claude.cmd`）。

```ini
EVAL_LLM_PROVIDER=claude_cli
# 下面都可选：
# EVAL_CLAUDE_MODEL=claude-sonnet-4-6   # 空=用 claude 自身默认模型
# EVAL_CLAUDE_TIMEOUT=600               # 单次调用超时(秒)，大文档出题可能较久
# EVAL_CLAUDE_BIN=claude                # 找不到命令时填 claude 全路径
# EVAL_CLAUDE_EXTRA_ARGS=               # 追加给 claude 的原始参数，空格分隔
```

工作原理：prompt 经 **stdin** 传入 `claude -p --output-format json`（避免命令行长度
限制），在**临时空目录**运行以隔离本项目的 `CLAUDE.md` 上下文；token 用量从返回
JSON 的 `usage` 字段解析。

> ⚠️ 每次调用会带上 Claude Code 自身的 system prompt，所以报告里"框架成本"的
> prompt token 会偏大、首次有缓存写入成本——属正常现象，不是 bug。

### 方式二：Anthropic API 直连

```ini
EVAL_LLM_PROVIDER=anthropic
ANTHROPIC_API_KEY=sk-ant-...
EVAL_ANTHROPIC_MODEL=claude-sonnet-4-5
# 走中转网关时再加：ANTHROPIC_BASE_URL=https://your-gateway/...
```

### 方式三：复用仓库内 llm_service（需其已在 :8900 运行）

```ini
EVAL_LLM_PROVIDER=llm_service
EVAL_LLM_SERVICE_URL=http://localhost:8900
```

> 改完 `.env` 后，**重启终端 1 的 eval-llm** 即可。验证：访问
> <http://127.0.0.1:8801/health> ，`provider` 字段应显示你选的 provider。

## 3. 完整使用流程（生成层：回答质量）

在前端 <http://127.0.0.1:8800> 上，从左到右、从上到下操作：

### ① 新建项目
左上输入项目名 → `+ 新建项目`。项目是一组文档/用例/评测的命名空间。

### ② 上传测试文档
左侧「文档」卡片选文件 → `上传并解析`。
- 支持 `.md` / `.markdown` / `.txt` / `.text` / `.chm`。
- `.pdf` / `.docx` 等暂不支持，请先转 markdown。
- `.chm`（微软帮助文档）解析需 Windows `hh.exe` 或 PATH 上的 `7-Zip`。

eval-api 会把文档解析为纯文本 + 分节，存进项目。

### ③ 出题（生成测试集）
左侧「出题」卡片：
- 勾选要覆盖的**问题类型**（factoid 事实 / conceptual 概念 / procedural 操作 /
  constraint 约束 / troubleshooting 故障 / navigational 导航）；
- 填「每类每文档」题数 → `生成测试集`。

eval-llm 以**一线操作员**视角，对每篇文档分型出题，每道题给出：**问题、期望答案、
评分要点(key_points)、黄金证据事实全集(expected_evidence)、黄金关键实体、出处**。
右侧会列出题目，点开可看期望答案/要点/出处。

> 已有现成用例集？跳过出题，用 [§5 导入](#5-用已有用例集导入-yamljson)。

### ④ 把题目交给被测 Agent，回填回答
这一步**在框架外做**：你拿这些问题去问被测 copilot Agent，拿到它的自然语言回答。
回到前端，逐题在文本框**粘贴回答**，并填：
- **查询时长(ms)**：被测 Agent 回答这道题花的时间；
- **Agent token**：被测 Agent 自己消耗的 token（用于成本统计）。

填完点 `保存回答`。
> 当前回答经**人工上传**（被测 Agent 接口尚未约定，故先解耦）。未填回答的题会被
> 判为 `missing`、计 0 分。

### ⑤ 运行评测
顶部 `运行评测`。eval-llm 裁判逐题把"被测回答"与"期望答案/要点"比对，给 0–1 连续
分 + 裁决（correct/partial/incorrect）。顶部即时显示总体/分型准确率。

### ⑥ 看报告
点 `↗ 打开完整报告` 看 HTML 报告（指标含义见 [§7](#7-报告怎么看)）。

## 4. 检索层评测（证据召回质量）

衡量"被测**检索器**召回的证据包对不对、排得好不好"，与生成层独立、可单独跑。
前端顶部从「生成层」切到「**检索层（证据召回）**」。有两条路：

### 4A. 人工上传检索证据（可算召回率）
逐题把检索器返回的证据**按排名、每行一条**粘进文本框 → `运行检索评测`
（默认 K=1,3,5,10）。eval-llm 对每个证据条目打 0–3 相关性等级，并判定每条黄金事实
最早被哪个条目覆盖，再确定性算出 HitRate / Recall / MRR / NDCG / ContextPrecision /
ContextRecall。
> 召回率族（Recall / ContextRecall）依赖用例里的**黄金事实**（见 [§6](#6-测试用例与黄金事实)）。

### 4B. 拉真实查询日志（精确率族，无需人工上传/无需黄金标注）
不想人工上传、也没黄金标注时，直接拉被测检索器的**真实流量**（`serving_query_logs`）评测：

1. 先在 `.env` 配 serving 库连接（未配该功能关闭、接口返回 503）：
   ```ini
   SERVING_PG_HOST=...
   SERVING_PG_PORT=5432
   SERVING_PG_DBNAME=...
   SERVING_PG_USER=...
   SERVING_PG_PASSWORD=...
   SERVING_PG_SSLMODE=disable
   ```
2. 在被测 Agent 上**真实查询一次**，然后在前端「检索层」下方「拉真实查询日志」区域，
   （可选填 domain）点 `评测最新查询`——框架拉**最近 N 条**（默认 1 条）真实查询评测。

框架按 query 重建「问题 + 按排名的证据条目」（证据文本由 item id JOIN
`asset_retrieval_units.text`），由 eval-llm 按与问题的相关性打分。
> 真实日志**无黄金标注**，只产出**精确率族**：HitRate / MRR / NDCG / ContextPrecision
> （+ 查询时长）；召回率族在报告中标记 `N/A（需黄金标注，后续开发）`。

## 5. 用已有用例集（导入 YAML/JSON）

已有人工整理好的用例，直接导入为一个 suite，**跳过出题、无需 eval-llm**。
左侧「导入已有用例」卡片上传 `.yaml`/`.yml`/`.json`。

顶层用 `questions:` 或 `cases:` 列表。单条字段映射（取首个存在者）：

| 框架字段 | 来源字段 |
|---|---|
| `id` | `id` / `case_id`（缺省自动 `q001…`） |
| `question` | `question` / `query` |
| `question_type` | `question_type` / `type` |
| `expected_answer` | `expected_answer` / `answer` |
| `expected_evidence`（检索层黄金事实） | `expected_evidence` / `expected_evidence_contains` |
| `expected_entities`（黄金关键实体） | `expected_entities` |
| `key_points` | `key_points`，否则合并 `expected_evidence_contains` + `expected_entities` |
| `source.section` | `source_section` / `source.section` |
| `difficulty` / `notes` | 同名字段 |

最小示例（YAML）：

```yaml
questions:
  - id: q001
    question: "默认 APN 是什么？"
    question_type: factoid
    expected_answer: "默认 APN 为 cmnet。"
    expected_evidence_contains: ["默认 APN 为 cmnet"]
    expected_entities: ["APN", "cmnet"]
    source_section: "APN 配置"
    difficulty: easy
```

> YAML 导入需 `pyyaml`（在 `requirements.txt` 里）；未装可改上传 `.json`。
> 未知 `question_type`、缺字段、重复 id 会返回 400 并指出具体行号。
> 仓库内已有现成样例：`data/knowledge_base/IP/数据中心网络搬迁到SDN最佳实践_eval_100.yaml`（100 题）。

## 6. 测试用例与"黄金事实"

**黄金事实（gold facts）= 回答一道题所必须命中的关键事实/证据片段的完整集合。**
它是检索层**召回率**（Recall@K / ContextRecall）的标尺：没有它，只能算精确率族。

本框架的原则是**在构建测试用例时就给出黄金事实全集**，两条路都已支持：

- **自动出题**：eval-llm 现在每道题都会产出 `expected_evidence`（黄金事实全集）+
  `expected_entities`（关键实体），无需事后补标。
- **导入用例**：在 YAML 里写 `expected_evidence_contains` + `expected_entities`
  （见 [§5](#5-用已有用例集导入-yamljson)）。

裁判时，框架把这些黄金事实交给 eval-llm，判定每条事实**最早被哪个检索条目覆盖**
（语义蕴含即可，不要求字面一致），据此算召回。

## 7. 报告怎么看

报告落在 `workspace/<project_id>/reports/<run_id>.{md,html}`，前端「打开完整报告」即访问。

### 生成层（回答质量）

| 指标 | 含义 |
|------|------|
| **按类型准确率** | 每类 `通过数/总数`；score ≥ 阈值(默认 0.6)计通过；未答计不通过 |
| **总体准确率** | 所有题通过数/总数 |
| **平均分** | 裁判 0–1 连续分均值（整体 + 分型） |
| **查询时长** | 来自你上传的时长：均值 / P50 / P95 / 最大 |
| **Agent token** | 被测 Agent 自身合计 + 每题均值 |
| **框架成本** | 框架出题/裁判 token（**与被测 Agent 分开**） |
| **裁决分布** | correct / partial / incorrect / missing 计数 |

### 检索层（IR，每个 K 各一份，并按问题类型分桶）

| 指标 | 含义 |
|------|------|
| **HitRate@K** | top-K 内至少命中一个相关条目计 1 |
| **Recall@K** | top-K 覆盖的黄金事实数 / 黄金事实总数 |
| **MRR@K** | 首个相关条目排名的倒数（>K 计 0） |
| **NDCG@K** | `DCG@K/IDCG@K`，用 0–3 分级 |
| **ContextPrecision@K** | top-K 中相关条目数 / `min(K, 实际返回数)` |
| **ContextRecall** | 任意排名下被覆盖的黄金事实数 / 总数（不限 K） |

## 8. 常见问题排查

**报错 `Unable to evaluate type annotation 'str | None'`**
→ 用了 Python 3.9。改用 `py -3.10`（或任意 ≥3.10）。

**`-m runtime_eval.eval_api` 报 `No module named 'runtime_eval'`**
→ 从 `runtime_eval/` 目录执行，并设 `PYTHONPATH` 指向该目录：
```bash
PYTHONPATH=/abs/path/to/runtime_eval py -3.10 -m runtime_eval.eval_api
```

**选了 `claude_cli` 但启动 eval-llm 报"找不到 claude"**
→ 确认命令行能直接跑 `claude`；不行就用 `EVAL_CLAUDE_BIN` 填全路径
（Windows 一般是 `...\npm\claude.cmd`）。

**`claude_cli` 调用超时**
→ 大文档出题较慢，调大 `EVAL_CLAUDE_TIMEOUT`（默认 600 秒）。

**上传文档报 415**
→ 传了暂不支持的二进制格式（.pdf/.docx 等），先转 markdown。`.chm` 需 `hh.exe` 或 `7-Zip`。

**评测报"尚无任何已上传回答"**
→ 该 suite 还没有任何非空回答，先逐题粘贴回答并 `保存回答`。

**eval-api 调 eval-llm 连接被拒**
→ 确认 eval-llm 已启动，且 `EVAL_LLM_URL` 指向它（默认 `http://localhost:8801`）。

**检索层「拉真实查询日志」接口返回 503**
→ 没配 `SERVING_PG_*`。配齐 serving 库连接后重启 eval-api。

**控制台中文乱码**
→ Windows 控制台代码页问题，不影响落盘——产物 JSON/报告均为 UTF-8。
（命令前加 `PYTHONIOENCODING=utf-8` 可改善控制台显示。）
