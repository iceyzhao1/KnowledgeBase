# 知识库本体自进化系统 — 设计文档

> 日期：2026-06-05
> 状态：方案讨论稿（high-level，未进入实现）
> 范围：knowledge_mining（挖掘侧）+ agent_serving（检索侧）+ databases / domain pack

---

## 0. 背景与目标

### 为什么要引入本体
现有检索是「BM25 + 向量 + 段落间 RST 关系」。本体的目的是给知识库**再加一个全新的检索角度**——实体与实体间关系构成的知识图谱视角，让系统能从「实体邻域」「沿关系多跳」的角度召回与推理，而不只靠字面相似和向量相似。

### 为什么本体必须「自进化」
本项目面向高度专业化的领域（云核网 5GC、IP 等）。这些领域**没有现成的、建好的完善本体**，而人工从零建一个完善本体耗时极长。现实起点只有：

- 一些**本体建立的规则**（怎样算一个合格的实体类型 / 关系类型）；
- 专家给出的**少量本体样本**（small samples）。

因此系统不能假设本体一开始就完整，必须是一个**边用边长、可自我进化**的本体系统。

### 一条重要原则：本体与文章正交
本体是独立的 schema（类型 + 类型间允许的关系），文章是语料，两者互不从属。挖掘时做的事情很纯粹：**在文章的每个片段里，按「当前本体」定义的点（实体）和边，把它们抽出来并存储**。不需要预先把片段分成「有本体的」和「没本体的」两类——抽取动作对所有片段统一。

## 1. 原始设计（用户提出）

### 1.1 心智模型：两层
| | 规则层（本体本身） | 事实层（实体实例） |
|---|---|---|
| 点 | 实体类型，如「网元」「接口」 | 具体实体，如 SMF、UPF、N4 |
| 边 | 类型间**允许的**关系类型，如「网元—可连接—接口」 | 实体间**实际的**关系，如「SMF—通过 N4 连—UPF」 |
| 变化速度 | 慢，需人审 | 快，每次挖掘自动产出 |
| 谁说了算 | 人（评审） | 机器抽取（受规则层约束） |

### 1.2 核心流程（原始 4 点，含澄清后的修订）
1. **统一抽取**：对每个片段，按当前本体把点（实体）和边抽出来、做实体消歧后存储。**不区分「有本体 / 没本体」的片段**，抽取动作对所有片段一致。
2. **本体自发现**：因领域本体不完善，需从「已有本体 + 文章知识」中发现新的本体元素，对候选**打分**并**人工评审**。
3. **回灌重抽**：新本体经评审并入后，回到步骤 1，按更新后的本体继续抽实体。

## 2. 设计缺口与解决方案

> 以下是对原始设计的查漏补缺。每条：**问题 → 方案**。

### 缺口 A — 自发现的「信号从哪来」
**澄清**：采纳「不按片段划分覆盖 / 未覆盖」的意见，抽取轨对所有片段统一。但**自进化轨道仍然需要一个信号源**，否则「发现新本体」没有输入。

**方案**：把系统拆成**两条轨道**：
- **抽取轨（快）**：所有片段统一按当前本体抽点+边+消歧+落地。
- **进化轨（慢）**：信号来自两处——
  1. **逃生口（byproduct）**：抽取时让 LLM 顺带报告「看着重要、但当前本体里没有对应类型 / 关系的概念」，作为候选。注意这不改变抽取对片段的统一处理，只是抽取的一个附带输出。
  2. **全局归纳 pass**：定期扫整批语料 + 当前本体 + 建模规则 + 专家样本，主动归纳候选新类型 / 新关系。

两条轨道解耦：抽取轨永远用「当前已批准的本体版本」；进化轨负责把本体养厚，批准后再触发回灌。

### 缺口 B — 缺少「事实边」的抽取步骤（回答原始第 4 点）
原始 1/2/3 步里只有「点」，没有任何一步在抽实体间关系。**边需要单独建，且分两种、在两个地方建**：

1. **规则层的边（关系类型）**：如「网元类 可以连 接口类」。这是棋规，不是从某段话直接抽的事实，它跟新类型一样在**进化轨的发现 + 人审**里产出。
2. **事实层的边（实体实际关系）**：如「SMF—通过 N4—UPF」。这是棋子实际走法，在**抽取轨、实体消歧之后**新增一个「关系抽取」阶段产出，并受规则层约束校验（本体不允许的关系类型直接拦掉）。

**补充（跨片段问题）**：边连接的实体常常分布在不同片段 / 不同文档。所以：
- 片段内只能抽到「局部 mention 级的边」；
- 真正的知识图谱需要在**全局阶段**：先把所有片段的实体 mention 消歧成 canonical 实体，再把局部边对齐 / 合并 / 连成跨文档的图。

因此抽取轨末尾顺序为：**抽实体 mention →（全局）消歧归一 →（全局）抽并对齐事实边 → 落地图谱**。

### 缺口 C — 缺少本体版本治理（支撑原始第 3 点的回灌重抽）
原始第 3 点「新本体并入后继续抽」，但没说怎么不全量重跑。本体一变就重挖全部文档，代价爆炸。

**方案**：
- **本体本身带版本号**；每次挖掘 run 记录「本次使用的本体版本」。
- 本体升版后**只增量重抽**受影响的文档（如当初通过逃生口贡献过该候选、或包含相关实体的文档），而非全量重跑。
- 实体 / 边记录「在哪个本体版本下抽出」，便于追溯与差异比对。

### 缺口 D — 打分缺了最关键的「语料级证据」维度
原始第 2 点说要「打分」，但单篇文档不能决定一个新类型（可能是生僻或笔误）。

**方案**：发现新本体做成**全局阶段**，打分至少包含：
- **跨文档频次 / 分布**：该候选在多少篇文档反复出现（语料级证据，最关键）；
- **与既有类型的区分度**：是不是其实已被某个现有类型覆盖；
- **与专家样本 / 建模规则的契合度**；
- **内部一致性**：多篇文档对它的用法是否一致。

流程：LLM 给初评分 → 低分自动丢弃 / 中分进队列 / 高分置顶 → 人只复核高价值候选。

### 缺口 E — 自发现的对象既有「点类型」也有「边规则」
原始第 2 点容易只想到发现新「类型（点）」。但本体还包含**类型间允许的关系（规则层的边）**，这同样需要被发现 + 人审。

**方案**：进化轨同时产出两类候选——**新实体类型** 和 **新关系类型**，走同一套打分 + 人审通道。

## 3. 整体架构（两轨 + 闭环）

```
                       ┌──────────────────────────────────────────┐
                       │  本体（规则层）：实体类型 + 关系类型 + 约束  │  有版本号
                       │  起点 = 建模规则 + 专家小样本               │  人审批准
                       └───────────────┬──────────────────────────┘
                          约束 │                    ▲ 批准后升版
        ┌───────────────────────┼────────────────────┼──────────────────────────┐
        ↓ 抽取轨（快，每次挖掘）                        │ 进化轨（慢，人审闭环）
  每个片段统一处理：                                    │
   抽实体 mention（开逃生口）───────逃生口候选──────────►  候选池
        ↓                                              ▲   ↑ 全局归纳 pass
  （全局）实体消歧归一 → canonical 实体                 │   （扫语料+规则+样本）
        ↓                                              │
  （全局）抽事实边（受规则层校验）─局部新关系信号────────►  候选打分（语料级证据）
        ↓                                              │       ↓
  落地知识图谱（实体表 + 关系表 + mention 链接）         │   人工评审（点类型 & 关系类型）
        ↓                                              │       ↓
  供检索侧消费（实体链接 / 图扩展召回 / 本体重排）       └───并入本体 + 升版 + 增量回灌重抽
```

### 3.1 在现有挖掘流水线中的落点
现有：`parse → segment → enrich(抽段内实体) → relations(段落间 RST) → retrieval_units → embedding → db_write → (全局)assemble_build / publish`。

新增 / 改造：
- `enrich` 阶段：实体抽取改为「受本体约束 + 开逃生口」。
- 新增**全局阶段**：实体消歧归一 → 事实边抽取与对齐 → 图谱落地。
- 新增**进化轨**（可独立 job）：全局归纳 → 候选打分 → 人审工具 → 本体升版 → 增量回灌。

### 3.2 新增数据表草案（先在 PostgreSQL 上做，暂不上图库）
| 表 | 作用 |
|---|---|
| `ontology_versions` | 本体版本（规则层快照），记录类型集、关系类型集、生效状态 |
| `ontology_entity_types` / `ontology_relation_types` | 当前本体的点类型、边规则（含允许的 head/tail 类型约束） |
| `asset_entities` | canonical 实体（消歧后的规范档案：规范名、别名、所属类型、本体版本） |
| `asset_entity_relations` | 事实层的边（head 实体、tail 实体、关系类型、置信度、本体版本） |
| `asset_segment_entity_mentions` | 段落 → 实体 的 mention 链接（原始 mention 文本、所在片段、消歧到的 canonical 实体） |
| `ontology_candidates` | 候选本体（候选类型 / 候选关系、来源逃生口或归纳、打分、评审状态：proposed/queued/accepted/rejected） |

所有 asset_* 表与现有 build / release 版本机制对齐（属于某个 build，随 release 激活）。

## 4. 检索侧（agent_serving）如何消费
1. **查询理解**：用本体把用户口语映射到 canonical 实体（实体链接），不靠字面碰运气。
2. **图扩展召回（GraphRAG 核心）**：命中实体后沿 `asset_entity_relations` 扩展 N 跳，召回结构化知识邻域。
3. **本体重排**：概念相关的优先于字面相似的。
4. **上下文组装**：把实体卡片 + 关系子图喂给下游 LLM，支持多跳推理。

---

## 5. 分期落地建议
- **一期（抽取轨主路）**：本体约束抽实体 + 消歧 + 事实边 + 图谱落地 + 逃生口埋点。即便本体还小，也先把「实体/边」这个新检索角度跑通。
- **二期（进化轨闭环）**：全局归纳 + 候选打分 + 人审工具 + 本体版本治理 + 增量回灌重抽。
- 检索侧的图扩展 / 本体重排可在一期数据就绪后渐进接入。
