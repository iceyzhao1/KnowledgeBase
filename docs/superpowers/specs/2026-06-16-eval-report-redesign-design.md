# 评分报告页重设计（综合总评 + 正式标题 + 指标注释）

- 日期：2026-06-16
- 范围：`runtime_eval` 的 eval-web 前端（`app.js` / `styles.css`）+ eval-api 后端 + eval-llm 服务
- 背景：当前「评分报告」页（工作流第 4 步）标题抽象、不统一、顺序无逻辑——「评估报告」其实是 L1 检索层报告，「评估标准」是一堆没人看得懂的裸参数，L1/L2/L4 代号外人不知所云；三层各出各的小报告，缺一个把它们捏到一起的总报告；大量专业指标没有解释，用户看不懂说明了什么。

---

## 1. 目标

1. **标题正式化、顺序逻辑化**：三层用「检索质量 / 答案质量 / 增量价值」正式叫法，每个标题下配一句话解释；按「找资料 → 答案 → 价值」的逻辑顺序排列。
2. **新增综合评分**：页面置顶一张综合卡，把三层结果汇总成关键数 + 状态徽章，并调用一次 `claude -p` 生成一段**自然语言总评**——不只给达标/不达标结论，而是用大白话解释这些指标说明了知识库好在哪、差在哪、该往哪改。
3. **每个指标加注释**：检索质量/答案质量/增量价值每一段里，每个指标名旁挂一个小说明（hover tooltip + 一行小灰字），点出该指标含义；打分口径卡同理。
4. **打分口径折叠收尾**：原「评估标准」改名「打分口径」，折叠到页面底部，每个参数配大白话。

非目标：不改三层各自的计算/跑批/SSE 逻辑；不动 L3（后端有但当前页面未单独展示）；不改后端评分口径数值。

---

## 2. 页面结构（从上到下）

```
评分报告（工作流第 4 步）
├─ 0. 综合评分                ← 新增，置顶
│    ├─ 三栏关键数 + 状态徽章（检索质量 / 答案质量 / 增量价值）
│    ├─ [生成综合评价] 按钮
│    └─ Claude 自然语言总评（哪层没跑标「未评测」）
├─ 1. 检索质量（L1）          ← 原「④ 评估报告」+ 底部逐题检索卡片
├─ 2. 答案质量（L2）          ← 原「答案对照」
├─ 3. 增量价值（L4）          ← 原「增量价值」
└─ 4. 打分口径（折叠）        ← 原「评估标准」
```

旧顺序里「④ 评估报告 → 增量价值(L4) → 答案对照(L2)」编号和层级对不上，新顺序按数据依赖与阅读逻辑：先看找得准不准（基础），再看谁答得好，最后看整库值不值。

## 3. 标题与文案表

| 段 | 正式标题 | 副标题（小灰字，一句话解释） | 代号 |
|---|---|---|---|
| 0 | **综合评分** | 汇总三层结果，由 Claude 给出整体评价与改进建议 | — |
| 1 | **检索质量** | 知识库能不能把对的资料捞出来 · 命中率 / 排序质量 / 召回 | L1 |

| 4 | **打分口径** | 本次按什么标准打分（点开过目） | — |

L1/L2/L4 代号缩成标题旁的小徽章保留，方便追溯。

## 4. 综合评分卡（核心新增）

### 4.1 前端 UI

- **三栏关键数**：每栏标题 + 一个代表数 + 状态徽章。
  - 检索质量：通过率 `pass_rate`（无黄金时退回 KB 综合分），徽章按通过率阈值判达标/不达标。
  - 答案质量：最佳模型名 + 其综合分 `f1`。
  - 增量价值：净增量 `net_uplift`，徽章用后端已有的 `value_pass`（值得建/暂不达标）。
  - 某层尚无结果 → 显示「未评测」灰徽章。
- **[生成综合评价] 按钮**：点击调 `POST /api/v1/suites/{sid}/overall`，loading 态。
- **自然语言总评区**：渲染 Claude 返回的中文总评纯文本（保留换行）。页面初次加载时调 `GET` 取上次已存的总评（没有则提示「点上方按钮生成」）。

### 4.2 后端（沿用现有「prompts + service + 端点」三件套）

1. `eval_llm/prompts.py` 新增 `build_overall_summary_prompt(*, suite_meta, l1, l2, l4) -> (system, user)`：把三层关键指标（含哪层缺失）整理进 user prompt；system 要求 Claude 用**中文、大白话**，先一句话结论，再分点解释每层指标说明了什么、知识库的强弱项、给出可执行改进建议；缺失的层如实说明「该层未评测」。
2. `eval_llm/service.py` 新增 `summarize_overall(provider, *, suite_meta, l1, l2, l4) -> {"summary": str, "usage": dict}`：`provider.chat(json_mode=False, ...)`，返回总评正文 + token 用量。
3. `eval_llm/app.py` 新增 `POST /overall-summary`（`OverallSummaryIn`：suite 元信息 + 三层 metrics dict，缺层传 None）。
4. `eval_api/llm_client.py` 新增 `summarize_overall(...)` 方法 → POST `/overall-summary`，超时放宽（同 judge 级别即可）。
5. `eval_api/app.py` 新增：
   - `POST /api/v1/suites/{sid}/overall`：用 `store.latest_run_summary(sid, layer=...)` 读 L1(`retrieval`)/L2(`answer_match`)/L4(`value`) 三层 metrics（缺的传 None）→ 调 `client.summarize_overall` → 存 `RunSummary(run_id=f"overall_{sid}", layer="overall", kind="synthesis", metrics={"summary": text, "headline": {...三层关键数...}})` → 返回 `{run_id, summary, headline}`。
   - `GET /api/v1/suites/{sid}/overall`：取已存的 `overall_{sid}` 总评；无则 404。
   - 三层全缺时 `POST` 返回 400「三层都还没评测」。

> 通俗：把三场考试（找资料、答题、值不值）的成绩单拼成一张，再请 Claude 当班主任写一段中文评语，告诉你这库到底行不行、哪儿弱、怎么改。

## 5. 指标注释（每层 + 口径卡）

**原则：凡是页面上展示出来的数字、徽章、诊断桶，都要带注释**——一个都不能裸奔。每个指标名旁加 `title=` tooltip（hover 显示）+ 必要处一行小灰字。统一文案：

**检索质量（L1）**（当前摘要实际渲染：Context Recall / NDCG / Recall / HitRate / MRR / 已判数）
- 命中率 HitRate@K：前 K 条检索结果里，至少有一条是对的的题占比。
- 排序质量 NDCG@K：对的资料排得越靠前分越高。
- 召回 Recall@K：该找到的资料，前 K 条里找回来了多少。
- 平均倒数排名 MRR@K：第一条对的资料排得有多靠前（越靠前越接近 1）。
- 上下文召回 Context Recall：回答需要的要点，被检索内容覆盖了多少。
- 已判 / 总数：已完成评分的题数 / 测试集总题数。
- KB 综合分 / 通过率（若在最终报告/口径处展示）：找到×排名×质量加权总分 / 达到单题通过线的题占比。

**答案质量（L2）**
- 综合分 F1：覆盖度与准确度的调和平均，排行榜主排序。
- 覆盖度：黄金答案的要点命中了多少（防漏）。
- 准确度：模型说的论断里有多少被黄金答案支持（防掺水，矛盾算不准）。
- 硬伤：与黄金答案直接矛盾/编造的条数。

**增量价值（L4）**
- 净增量：用库相对闭卷，逐题分差的难度加权均值（正=库有用，负=库帮倒忙）。
- 胜率：用库明显更好的题占比。
- 负增量率：用库反而更差的题占比（帮倒忙）。
- 不可替代率：只有用库才答对的题占比。
- 诊断桶（逐题归类，要逐个加注释）：
  - 不可替代 exclusive：闭卷答错、用库才答对——这库的硬价值。
  - 锦上添花 boost：两边都还行，但用库明显更好。
  - 平局 tie：用库和闭卷差不多，库没帮上忙也没添乱。
  - 帮倒忙 regression：用库反而比闭卷更差。
  - 双输 both_fail：用库和闭卷都没答好。

**打分口径卡**（原裸参数补解释）
- 检索深度 K：每题看前几条检索结果。评分基准 K = 综合分按哪个 K 算。
- 综合分权重：找到/排名/质量各占多少。
- 单题通过线：召回、命中排名、上下文召回要达到的门槛。
- 难度加权：不同难度题的计分系数。
