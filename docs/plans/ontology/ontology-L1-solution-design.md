## 1. 目标与定位

### 1.1 要解决什么：从「找段落」升级到「任务闭环检索」
现有检索是「BM25 + 向量 + 段落间 RST 关系」，本质是"找相似段落"。本方案新增**知识图谱视角**，目标不是多一种召回，而是支撑**多跳 / 任务闭环**类查询，例如：
- "SMF 涉及哪些接口和对应协议？"（实体邻域多跳）
- "配置 N4 互通牵扯哪些网元和命令？"（跨对象组合）
- "PCF 策略下发到 UPF 执行，链路上有哪些环节？"（关系路径）

**成功标准（借鉴五层文档 §7）**：能支撑一条"任务闭环"——场景识别 → 概念召回 → 机制解释 → 方法输出 → 条件筛选 → 验证路径。这是价值锚点；本体建到哪、检索用到哪，都对着这个靶子。

### 1.2 本体的形状：五层工程知识本体（只借结构）
本体**不是扁平的实体类型清单**，而是五层语义结构（来自数通域参考文档，结构通用、内容按 5GC 重建）：

| 层 | 回答 | 在 5GC 的含义（示意） |
|---|---|---|
| **概念层 Concept** | 是什么 | 网元 / 接口 / 协议 / 命令 / 参数 / 告警 / 特性 |
| 机制层 Mechanism | 为什么 | PFCP 会话建立、QoS 调度、选择流程等动态原理 |
| 方法层 Method | 怎么做 | 配置 / 验证 / 排障的操作脚本（带输入/输出/前置/顺序/验证槽位） |
| 条件层 Condition | 何时用 / 禁忌 | 适用条件、约束、决策规则 |
| 场景层 Scenario | 什么业务背景下组合 | 端到端业务方案模式（带多槽位） |

**多跳的价值恰恰在跨层边**（场景→方法→概念→机制）。但跨层边、以及方法/场景这类"带槽位、跨章节合成"的对象，是最难自动抽的——价值与难度同在，因此必须分波。

### 1.3 落地从最底层（概念层）起步
> 本文其余章节描述的是**五层成熟态**；真正动手要分多阶段，**第一波（MVP）只落概念层**。本节只交代"先做哪层"，具体范围/批次/验收**〔计划见 L3〕**。

- **第一波只做概念层**：实体（概念对象）+ 概念层内部关系 + 出处 + 人审 + 冷启动，端到端跑通。
- cloud_core 现有 8 个实体类型基本就是概念层，可直接作为概念层的起点。
- 概念层候选关系（借结构、按 5GC 取用）：`is_a` / `part_of` / `instance_of` / `connects_to` / `belongs_to` / `uses_protocol` / `has_policy` / `provides_service` / `validated_by`；首波先启用哪几个 **〔计划见 L3〕**。
- **机制 / 方法 / 条件 / 场景四层后置**，且需跨章节合成，逐层加（路线见 §10）。
- **领域只做 cloud_core_network**。

### 1.4 既定原则与决策（2026-06-08）
| # | 决策 / 原则 |
|---|---|
| 本体形状 | 五层元模型，**MVP 只做概念层**，上层分波 |
| 领域 | 只做 **cloud_core_network**（数通文档仅作结构参考） |
| 本体真相源 | **存数据库、可被上传/人审写入**；冷启动用 `domain.yaml` 的 `ontology` 段引种成 v1，之后真相源转移到 DB，进化轨在 DB 上升版 |
| 出处（强约束） | **所有知识——图里的边、节点、文档片段——一律带"出处路径"**，落到 EvidenceNode → 片段 → 文档，不可为空 |
| 冲突 | **只标记、不合并**；多来源矛盾并存、各记出处，把矛盾暴露给人 |
| 消歧 | **由人拍板**，系统只给合并建议 |
| 人审 | **异常触发**（冒新类型 / 新实体 / 冲突 / 不确定才打断）；但**前端先把一切显式摊开**，早期用于 debug |
| 交互 | 全程 **kb-ui** 前端 |
| 存储 | 全部 **PostgreSQL**（含图）；读写图走一层薄接口，便于将来迁图库 |

### 1.5 本体与文章正交
本体是独立 schema，文章是语料。挖掘动作：在每个片段里，按当前本体把对象和关系抽出来存储；抽取对所有片段统一，不预先划分"有/无本体"的片段。

## 2. 心智模型

### 2.1 两层：规则层 vs 事实层
- **规则层（本体本身）**：五层的类型 + 每层内/跨层允许的关系类型 + 约束。慢变、人审。
- **事实层（实例）**：具体对象（如 SMF）与对象间实际关系。快变、机器抽（受规则层约束）。

> MVP 的规则层只激活"概念层"那一段；事实层只产出概念对象与概念关系。

### 2.2 两轨：抽取轨 vs 进化轨
- **抽取轨（快）**：每次上传文档，按当前本体抽概念对象 + 概念关系 + 消歧 + 落图。
- **进化轨（慢）**：冷启动 / 逃生口 / 全局归纳产出候选 → 打分 → 人审 → 升本体 → 回灌。

两轨解耦：抽取轨永远用已批准本体；进化轨负责养厚本体。

### 2.3 关键术语（大白话）
- **canonical 对象（规范对象）**：同一个东西在不同文章里有一堆叫法——"UPF""用户面功能""User Plane Function"说的都是它。**canonical 对象就是给这个东西定的"唯一户口"**：一个标准名（如 `UPF`）+ 一串别名 + 它属于哪个类型。挖掘时每篇文章里冒出的叫法叫 **mention（提及）**，消歧就是把这些 mention 都**认领到同一个户口**上。
  - 类比：很多快递单上写"老王""王经理""王建国"，canonical 对象就是身份证上那个"王建国"，别名表记着他还被叫做"老王/王经理"。
  - 为什么要它：没有户口，图里就会出现三个互不相连的"UPF"节点，跨文档的知识连不起来；有了户口，所有文章对 UPF 的描述都挂到同一个节点，邻域多跳才走得通。
- **mention（提及）**：某篇文章某一段里出现的一个具体叫法，是**文章级**的；canonical 对象是**领域级**的（全域共享，唯一）。
- **出处 / EvidenceNode**：每条知识"是从哪句话来的"的回链，落到 片段 → 文档。详见 §7。

## 3. 数据模型（全 PostgreSQL）

> 本节只回答"**有哪些表、各自干啥**"。**完整字段（DDL）、约束、索引一律〔实现见 L2〕**，本层不写字段，避免方案与实现串味。
> 一条贯穿原则：设计成"层可感知"——每个类型/对象带一个"所属层"的标记，MVP 只用 `concept`，将来加层不动表结构。

### 3.1 领域级（domain-scoped，领域内共享、累积）
| 表 | 说明 |
|---|---|
| `ontology_versions` | 本体版本快照（domain、版本号、状态、创建人） |
| `ontology_node_types` | 类型定义：name、**layer**、definition、attributes_schema、examples |
| `ontology_relation_types` | 关系类型（边规则）：name、**层内/跨层**、允许的 head/tail 类型、是否有向、反向名 |
| `ontology_entities` | canonical 对象：canonical_name、node_type、layer、aliases、attributes、ontology_version |
| `ontology_entity_relations` | 事实边：head、tail、relation_type、confidence、**source_refs（出处，强制非空）** |
| `ontology_alias_dictionary` | 别名词典（消歧产出，可种子自 `dictionaries/builtin_alias_hints.yaml`） |
| `ontology_candidates` | 候选本体：kind（node_type/relation_type）、layer、证据、打分、状态、来源（coldstart/escape_hatch） |
| `ontology_evidence_nodes` | **出处节点**：把任一对象/边链接到 段落片段 → 文档快照（实现"一切知识带路径"） |

### 3.2 文章级（document-scoped，绑定具体文档）
| 表 | 说明 |
|---|---|
| `asset_segment_entity_mentions` | 本篇片段 → 领域对象的 mention 链接：mention_text、node_type、resolved_entity_id、resolve_status（auto/human/pending） |

### 3.3 两处落地（呼应"一部分存文章、一部分存领域"）
- **文章级**：`asset_segment_entity_mentions`（本篇的 entity 部分）。
- **领域级**：新对象 → `ontology_entities`；新边 → `ontology_entity_relations`；本体新增 → `ontology_*`；别名 → `ontology_alias_dictionary`；出处 → `ontology_evidence_nodes`。
- 现有 `asset_raw_segments` / `asset_retrieval_units` 不改，新表通过 `segment_id` / `document_snapshot_id` 挂接；与 build / release 版本机制对齐。

## 4. 挖掘侧方案（抽取轨）

### 4.1 抽取目标（MVP = 概念层）
- 逐文档阶段 `entity_extract`（独立阶段，**双通道**）：抽**概念对象 mention**（受本体约束）+ **逃生口**（本体外但重要的概念，作候选）。`enrich` 只做篇章本职（语义角色 + 内容质量），不再兼抽实体。
- 新增全局阶段：**消歧归一**（mention → canonical 对象）→ **概念关系抽取**（受本体校验，软约束：不合法的高置信边转候选）→ **落图 + 出处**。

> 实现演进（2026-06-11）：MVP 期实体抽取曾**寄生在 `enrich` 的同一次 LLM 调用**里。后据 L4 §15/§16 决策**拆成独立 `entity_extract` 阶段**——独立 LLM 调用、本体类型表喂进 prompt、双通道输出（对齐已知类型 / 提议新类型）。本节文字已按拆分后的形态描述。

**抽取质量原则——特异性门槛**（借鉴 PRD EPIC-1）：一个东西配不配当概念对象，标准是"它能不能有自己的一条百科词条"。
- 抽：`SMF`、`N4 接口`、`PFCP`（有独立、可唯一标识的定义）；
- 不抽：`网元`、`接口`、`参数`、`配置`、`功能` 这类无限定的通用词、代词、抽象概念、时间引用、句子片段。
- 单段抽取数设上限，避免一段冒出几十个"伪实体"。这条门槛对所有片段统一生效，是落地前的质量底线。

### 4.2 顺序与跨章节（关键）
- 消歧必须在建边之前（边连 canonical 对象，非原始 mention）。
- 概念层关系多为**对象间直接关系**，单/邻近片段即可抽；
- **上层（机制/方法/场景）需要跨章节合成**（一个方法对象由多段拼成）——MVP 不做，二期单独设计"对象合成"阶段。
- 〔后置〕跨章节合成可复用 PRD EPIC-5 的 **Section 级分组**机制（按 `section_path` 把同一章节的片段聚合再分析），作为上层对象合成的基础设施。

### 4.3 软约束
本体不完善，校验闸口当**分流器**不当垃圾桶：合法边落地；高置信但本体不允许的边 → 转 `ontology_candidates` 当新关系信号，喂进化轨。

### 4.4 边的质量门槛与形状
点有"特异性门槛"（§4.1），**边也必须有自己的质量门槛**，否则图会被"两个词碰巧出现在同一段"这种伪关系灌爆。

**边的质量门槛——可断言性测试**（与点的"百科词条测试"对称）：一条边配不配落地，标准是"**它能不能被写成一句领域专家会点头确认、且脱离这段话的具体措辞仍成立的断言**"。
- 落：`SMF —connects_to→ UPF`（"SMF 通过 N4 与 UPF 连接"是稳定事实）；
- 不落：仅仅因为"SMF"和"计费"出现在同一段就连一条边（**共现 ≠ 关系**）。

由此引出边的几条硬规则（**具体阈值/指标〔实现见 L2〕**）：
1. **共现不等于关系**：要有"关系强度"证据，而不是同段出现就连。量化指标（NPMI 关联强度、共现频次、置信度阈值）见 L2。
2. **端点必须是已抽对象**：head/tail 必须来自本段已抽出的 canonical 对象，不凭空造点。
3. **禁自关系**：head ≠ tail。
4. **去语义冗余**：同一事实不重复落边。
5. **受本体约束（软约束）**：(head, relation, tail) 合法才落；高置信但本体不允许 → 转候选（§4.3）。

**边的形状**：落地的每条事实边除三元组外，带一句**自然语言事实描述**（如"SMF 通过 N4 接口与 UPF 连接"）——出处可读（人一眼看懂）、检索可用（下游 LLM 直接消费，不用回拼三元组）。

## 5. 进化侧方案（进化轨）

### 5.1 冷启动（概念层）= 用一份独立的「本体种子文件」引种
**决策（2026-06-09 修订）**：MVP 冷启动不走"自由抽 → 人审定第一版"那条重路，但也**不直接读 `domain_cloud_core.yaml`**。而是：
1. 把 `domain_cloud_core.yaml` 里那些类型/例子，**抽取沉淀成一份独立的「本体种子文件」**（专门描述本体 schema，格式即 §5.2 那套，**文件路径/格式〔实现见 L2〕**）；
2. 冷启动读**这份种子文件**，一次性引种成本体 **v1**（DB 即成真相源）；
3. 抽取轨用 v1 跑起来。

**为什么不直接读 domain.yaml**（这是关键原则，呼应原则③）：
- domain.yaml 是 mining/serving 的运行配置，**职责是"跑流水线"**，不该兼任"本体真相"。把本体 schema 混在里面会让两件事互相绑死。
- 独立种子文件**可复用**：它和将来专家上传的"本体定义文档"是**同一种东西、同一套格式**（§5.2），新领域、新一波本体都能照搬这个入口，而不是每次去改 domain.yaml。
- 引种之后真相源转移到 DB，种子文件只是"出生证"，进化轨在 DB 上升版。

> "自由抽 → 候选 → 人审" 这条路**不消失**，它退化成进化轨的常规手段（§5.3 逃生口/全局归纳），用来在 v1 之上发现种子没覆盖的新类型/新关系，而不是用来"造第一版"。这样第一刀就能跑，省掉一次重型人审循环。

### 5.2 种子本体也走"上传"（呼应原则③）
把专家写的本体定义当成一种**特殊文档类型「本体定义文档」**，走同一上传入口，喂的是规则层（schema）而非事实层。于是系统有两类上传：**知识文档**（抽实例）与**本体文档**（定/扩 schema）。不依赖写死的 YAML。

**本体定义/引种格式**（采纳 PRD EPIC-1/2/4 的 `entity_schema` 结构，已决策）：用结构化 YAML/表，一个本体定义至少含——
- `types`：每个类型带 `name` / `description` / `examples`；
- `aliases`：canonical → 别名列表（喂别名词典）；
- `relation_types` + `patterns`：关系名 + 允许的 `(head, relation, tail)` 组合。
这套结构既是 MVP 冷启动从 `domain.yaml` 引种的格式，也是将来专家"本体文档"上传的格式，两者统一。

### 5.3 候选打分与噪声剪枝（含语料级证据）
单篇不能立类型。打分思路：跨文档频次/分布、与既有类型区分度、与专家样本契合度、内部一致性。LLM 初评 → 人复核高价值候选。
**频率/度数排序双用**（借鉴 PRD EPIC-1 的 GraphRAG 思路）：跨文档频次与图中连接度不仅给候选打分，也用于**抽取轨剪低价值实体**——只在极少处出现、且无任何连接的孤立 mention 视为噪声过滤掉，避免图被生僻词/笔误灌爆。

> 打分不能拍脑袋，要用学界成熟指标：概念候选用 **termhood / 领域相关度 DR / 领域共识度 DC**，多词术语加 **unithood（NPMI）/ C-value**；关系候选用 **NPMI 关联强度 + 三级可信度**。**完整指标定义、阈值、计算口径〔实现见 L2〕**。

## 6. Human-in-the-loop 与透明前端

### 6.1 两道人审 Gate（异常触发）
- **Gate 1 本体评审**：冒出候选类型/关系时打断，人通过/改名/拒绝。
- **Gate 2 实体确认（消歧）**：拿不准的合并由人拍板。
- 本体趋稳后，无候选、无歧义则**自动放行**；人审是异常中断，不是必经关卡。

### 6.2 透明优先（呼应原则⑤）
早期阶段，前端**把抽取全过程显式摊开**：每段被标到哪些类型、画了哪些边、哪些冲突、哪些不确定，都看得见。目的是 debug——先看清哪一步没搞好，再谈自动化。

---

## 7. 冲突与出处（呼应原则④）
- **出处强制**：每个对象、每条边至少挂一个 `ontology_evidence_nodes` → 片段 → 文档，不可为空。图里的、文档里的知识都要可追溯到路径。
- **冲突只标记不合并**：多来源矛盾（如默认值 A 说 30s、B 说 60s）并存，各记出处；检索侧呈现时可提示"存在多来源/冲突"。
- 〔后置〕冲突模型可演进到**时间有效性**（借鉴 PRD EPIC-4 Graphiti 的 `valid_at` / `invalid_at`）：给边标"何时为真/何时失效"，从而区分"矛盾"与"版本演进"。MVP 先只做标记。

---

## 8. 检索侧消费（agent_serving）
- **MVP（概念层）**：实体链接（含别名词典）+ 概念邻域多跳召回 + 出处回链。已能回答"SMF 涉及哪些接口/协议"这类查询。
- **反向链接遍历**（借鉴 PRD EPIC-3 的 MENTIONED_IN 模式）：另起一路通道——查询里识别出的实体 → 查"哪些片段提到过它" → 直接召回这些片段。与邻域多跳互补：一个走"实体间的边"，一个走"实体↔片段的链接"。
- **完整（加上层后）**：跨层任务闭环检索（场景→条件→方法→概念/机制），对齐 §1.1 成功标准。
- 本体重排：概念相关优先于字面相似。
- 〔后置〕**全局/社区视角**（借鉴 PRD EPIC-7 的 GraphRAG global search）：对实体聚类成社区、生成社区摘要，支撑"这批文档整体讲了哪些主题/有何共性"这类**全局概览型**查询——这是"多跳任务闭环"之外的另一类价值，MVP 不做。

---

## 9. 存储与后期迁图
MVP 全 PG，概念层图规模小，递归 CTE 跑多跳无压力。守一道纪律：**图的读写藏在一层薄接口后**（至少"写图""按对象扩展 N 跳"），后期迁图库（如 NebulaGraph）= 换实现 + ETL，不动挖掘/检索业务逻辑。

> 迁图不是"导数据"那么简单，真正的成本与风险在**读路径查询重写**（递归 CTE → nGQL/Cypher）、**build/release 版本过滤**怎么在图库里表达、以及**事务/一致性模型差异**。**完整迁移风险分析〔实现见 L2〕**，这层只立"留薄接口"这道纪律。

## 12. 本体归纳重排：实体先确认、再归纳本体（2026-06-11 提案，待审）

> **状态**：**已实施**（2026-06-12，N1–N5 全部落地）。已取代 §4.1（逃生口直接产候选）、§5.3（候选打分时机）、§6.1（两道检查点 的顺序）的相应描述。实现设计见 **L2 §15**，分批见 **L3 §10**。

### 12.1 缘起：现在是"用没洗过的实体去造类型"
现行 `entity_extract` 一次 LLM 调用同时干两件事：把能对上的实体归到已有类型（通道 A），把对不上的概念**直接**写成本体候选（通道 B → `ontology_candidates` → 本体确认）。问题在于：喂给"造新类型"的那批概念，是**模型刚吐出来、没人验过的原始输出**——垃圾进垃圾出，类型提议继承了抽取噪声；而且这批"本体外概念"**绕过了 实体确认**，从不经过人工实体确认。

> 先澄清一个常见误解：抽取是**逐段**调 LLM，模型从不一次看多篇、甚至看不到整篇，所以"多篇一起导致上下文爆掉"在本架构里不存在；"全局"那一步（落图）是纯数据库聚合，不调模型。

### 12.2 新顺序：实例先确认，再从干净实例归纳类型
把"抽实体"与"归纳本体"拆成**两次 LLM 调用**，中间插入**人工实体确认（实体确认）**：

1. **抽实体（LLM 调用 1，逐段）**：抽 mention。能对上已有类型 → 直接归类；对不上但重要的 → 标成"**候选实体·暂无类型**"，**作为待确认实体进 实体确认**（不再直接变类型候选）。
2. **实体确认（人先确认所有实体）**：逐条裁决——并到已有对象 / 新建对象 / 丢弃（非实体）；对"暂无类型"的，确认它"**确实是个重要东西、只是还没有类**"。
3. **归纳本体（LLM 调用 2）**：只拿这批**人工确认过、但暂无类型**的实体（带跨文档频率与出处）去**聚类、归纳、命名新类型**，产出 `ontology_candidates`。
4. **本体确认（人确认新类型）**：通过 / 改名 / 拒绝 → 升版。
5. 升版后，之前"暂无类型"的实体补绑到新批准的类型；再做关系抽取 + 落图 + 建库发布。

### 12.3 为什么 实体确认 在前、本体确认 在后（与原顺序的本质区别）
- **质量**：用**人洗过的实体**归纳类型，远比用原始抽取结果准——这是核心收益。
- **顺序自洽**：用"**分两波绑定**"化解"类型必须先于实例"的死结——能对上老类型的实体在 实体确认 就绑好；新类型的实体在 本体确认 升版后才绑。"类型先于实例"对新类型那批仍成立，只是绝大多数实体在 实体确认 先确认完。
- 与现行"本体确认 在前"是**本质区别**：现在是先定类型（基于脏数据）再确认实例；新方案是先确认实例（干净）再归纳类型。

### 12.4 代价与适用（已接受）
- **两次暂停**（实体确认、本体确认 各一次），编排复杂度 +1；但 `subloop_stage` 断点机制本就支持多检查点。
- **稳态下基本零额外成本**：本体够用时没有"暂无类型"实体 → 不触发归纳、不触发 本体确认；实体确认 也仅在有歧义实体时才停。两次暂停只在"真发现新类型"时才完整发生——这恰好说明本体建得好。
- **归纳调用很便宜**：调用 2 处理的是一份紧凑、去重的已确认实体清单，不是重扫全文。
- 与既有"进化轨·全局归纳"（§5.3、§2.2）方向一致，是它的正式形态。
