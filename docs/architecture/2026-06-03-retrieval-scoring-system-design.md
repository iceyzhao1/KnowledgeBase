## 0. 层级总览（L0 / L1 / L4）

> **2026-06-16 扩充说明**：本文档原为 **L1 检索层**评分体系（§1–§11，内容保持不变）。现按分层评估框架补齐 L1 的**上下游两层**——下游根因层 **L0 知识资产**（§12）与上层价值层 **L4 业务价值/对照组**（§13）。三层共用同一套题集与答案事实包 F，指标可互相印证、根因可逐层下钻。

| 层 | 评什么 | 一句话 | 本文位置 | 与 L1 的关系 |
|---|---|---|---|---|
| **L4 业务价值** ⬆ | 用库 vs 不用库的**增量价值** | 这库到底**值不值得建** | §13 | 复用 L1 的题与事实包 F，加「对照组」 |
| **L1 检索层** | 召回片段**找得到/排得准/够答全** | 找得**准不准**（原核心） | §1–§11 | 本层 |
| **L0 知识资产** ⬇ | 本体/图谱/切块/嵌入的**质量** | 知识**本身好不好**（病根） | §12 | L1「空召回/不可答」的**下钻根因层** |

**为什么要上下两层**：L1 分低往往不是检索的错——可能是 L0 把关键事实切碎了、或源头压根没这知识（病根在下）；而 L1 分高也不等于业务有用——中间还隔着「会不会编造、agent 会不会用、到底比通用模型强多少」（价值在上）。L0 管**根因**，L4 管**价值**，L1 管**现状**。

## 1. 目标与范围

只评价**检索层**：给定一个问题，知识库召回的"证据包（chunk 列表）"质量好不好。
不评价生成层的语言流畅度，但会用**答案事实包**衡量"召回的内容够不够回答问题"——这是检索层和生成层之间的桥梁指标。

一句话定义"知识库好坏"：

> 对一组有标准答案的问题，知识库能否**把对的证据召回来（找得到）**、**排在前面（排得准）**、**少夹带噪声（纯度高）**、并且**召回的内容足以支撑答案中的每一条事实（答得出）**。

---

## 2. 三个输入物料（"三包"模型）

每道评测题由三部分构成，对应 YAML 评测集里的字段：

| 物料 | 中文 | YAML 字段 | 角色 | 粒度 |
|---|---|---|---|---|
| **Q** | 问题 | `question` | 被测查询 | 一句话 |
| **E** | 证据包 | `expected_evidence_contains` | 期望出现在召回 chunk 文本里的 verbatim 子串集合 | chunk 级定位信号 |
| **F** | 答案事实包 | `answer_facts`（**待新增**，从 `expected_answer` 拆解） | 标准答案拆成的原子事实/要点 | claim 级充分性信号 |

**为什么要把 E 和 F 分开？** 二者衡量的是不同的失败模式：

- **证据包 E** 回答：*"对的 chunk 有没有被召回？"* —— 定位能力，子串匹配即可判定（与现有 `runner.py` 一致）。
- **答案事实包 F** 回答：*"召回的这一包内容，够不够把问题答全？"* —— 充分性/可回答性。这一项才是真正反映"知识库对业务有没有用"的指标：你可能召回了相关 chunk（E 命中），但 chunk 被切碎导致关键事实缺失（F 不全）。

> 设计原则：**E 管"找得到"，F 管"答得出"。两者都过，检索层才算合格。**

---

## 3. 记号与基础判定

- 召回结果：有序 chunk 列表 `items[0..N-1]`，取 Top-K（默认 `K=10`）。每个 chunk 有 `text / score / route_sources / source_ref`。
- 证据包 `E = {e₁,…,e_m}`，`m = |E|`。
- 答案事实包 `F = {f₁,…,f_p}`，`p = |F|`。
- **chunk 相关性判定（与 runner.py 对齐）**：chunk `cᵢ` 相关 ⟺ 至少有一个 `eⱼ`（小写化后）是 `text(cᵢ)` 的子串。
- **证据命中秩** `rank(eⱼ)` = 满足 `eⱼ ∈ text(cᵢ)` 的最小下标 `i`，找不到记为 `∞`。
- `rank_first` = 第一个相关 chunk 的下标（0-based）。

## 4. 六个检索层指标

| # | 指标 | 来源物料 | 公式（单题） | 衡量什么 |
|---|---|---|---|---|
| 1 | **HitRate@K** 命中率 | Q+E | `1` 若 Top-K 内存在相关 chunk，否则 `0` | 找没找到（粗粒度门槛） |
| 2 | **Recall@K** 证据召回率 | Q+E | `|{eⱼ 在 Top-K 内被命中}| / m`（**去重**） | 证据包覆盖了多少 |
| 3 | **MRR@K** 首位相关秩 | Q+E | `1 / (rank_first + 1)` | 第一条有用证据排多高 |
| 4 | **NDCG@K** 排序质量 | Q+E | `DCG / IDCG`，二元增益 | 相关 chunk 整体是否靠前 |
| 5 | **Context Precision@K** 上下文精确率 | Q+E | `|{Top-K 内相关 chunk}| / min(K, |items|)` | 噪声率 = `1 − Precision` |
| 6 | **Context Recall** 事实可回答率 | Q+F | `|{被支撑的事实}| / p` | 召回内容够不够答全 |

### 4.1 关键细节

**Recall@K 必须去重。** 现有 `runner.py:120-123` 用 `matched_evidence.extend(matches)`（list 累加再除以 `len(expected)`），同一证据串在多个 chunk 命中会被重复计数，导致 Recall 可能 **> 1.0**。正确定义是按**不同证据片段**计数：

```python
found = {e for e in expected for item in items[:k] if e.lower() in item["text"].lower()}
recall = len(found) / max(len(expected), 1)   # 恒在 [0,1]
```

**Context Precision@K** 现有 runner **完全没算**，是当前最大的盲区——无法区分"精准命中"和"撒大网命中"。两者 Recall 可能一样，但后者用户体验很差。

**Context Recall（事实可回答率）** 需要答案事实包 F，分两档实现：

- **Tier 1 — 关键词覆盖（确定性、零成本）**：每条事实 `fₖ` 预先标注它的必需关键词/实体集合 `kw(fₖ)`；若 Top-K 召回文本的并集包含 `kw(fₖ)` 的全部（或 ≥θ 比例，θ 默认 0.8），则判 `fₖ` 被支撑。
- **Tier 2 — LLM 裁判（贴近 RAGAS）**：把 Top-K 召回文本 + 事实 `fₖ` 一起送 `/judge`，问"该事实是否被上下文蕴含/支撑？yes/no"。更准但有 token 成本，建议对 hard 题或抽样使用。

## 5. 单题综合分 S_q

把六个指标归并为三个**能力维度**，每维 ∈ [0,1]，再加权：

| 维度 | 含义 | 计算 | 来源 |
|---|---|---|---|
| **score_find** 召回能力 | 对的证据找得到吗 | `Recall@K` | E |
| **score_rank** 排序能力 | 对的证据排得靠前吗 | `0.5·MRR@K + 0.5·NDCG@K` | E |
| **score_quality** 纯度与充分性 | 这一包干净且够答吗 | `α·Precision@K + (1−α)·ContextRecall`，α=0.4 | E+F |

```
S_q = w_f · score_find + w_r · score_rank + w_q · score_quality
默认权重：w_f = 0.40，w_r = 0.25，w_q = 0.35
```

**权重依据**：召回是必要前提（没召回到就无从谈起），权重最高；但"纯度+可回答性"才真正反映知识库**对业务的有用性**，所以 quality 权重高于 ranking；当 K 适中时，排序是次要矛盾。`score_quality` 内部把可回答性（1−α=0.6）压过精确率（α=0.4），因为"答不出"比"有点噪声"更致命。

> 权重不是定死的，是可调旋钮。建议把 `(w_f, w_r, w_q, α, θ, K)` 写进配置，按场景调。

## 6. 失败诊断分类（比分数更重要）

聚合分会掩盖"为什么差"。每道题归入唯一一个诊断桶，告诉你该拧哪个旋钮：

| 桶 | 判定条件 | 病根 | 对应处置 |
|---|---|---|---|
| **空召回 Empty** | `items` 为空 | 索引/路由失败 | 检查 ingest、route 命中 |
| **错召回 Miss** | `items` 非空但 `Recall@K = 0` | 相关性/embedding 差 | 换/微调 embedding，扩同义词 |
| **低排序 Buried** | `Recall>0` 但 `rank_first > 3` | 排序/rerank 差 | 引入或调 reranker |
| **高噪声 Noisy** | `Precision@K < 0.3` | 过召回/切块过大 | 调 Top-K、收紧阈值、改 chunk |
| **不可答 Unanswerable** | `Recall>0` 但 `ContextRecall < 0.8` | 切块割裂/源覆盖缺口 | 改 chunk 策略、补源文档 |
| **健康 Healthy** | 通过下方 PASS 标准 | — | — |

这个分类是诊断核心：**同样 0.6 分**，是因为"排得靠后"还是"夹带噪声"还是"答不全"，处置完全不同。

## 7. 单题 PASS 标准与 KB 级聚合

**单题 PASS**（headline 健康判定）：

```
PASS ⟺ Recall@K ≥ 0.5  且  rank_first ≤ 3  且  ContextRecall ≥ 0.8
```

**按难度加权聚合**（hard 题权重更高，更能拉开知识库差距）：

```
难度权重 w_d：easy = 1.0，medium = 1.5，hard = 2.0
KB 检索质量分 = Σ_q (w_d · S_q) / Σ_q w_d
KB 通过率     = Σ_q (w_d · [PASS]) / Σ_q w_d
```

输出报表建议**分层呈现**：

- 总分 + 通过率（headline）
- 按 `question_type`（factoid/conceptual/procedural/constraint/...）分组
- 按 `difficulty` 分组
- 六个原始指标的均值
- 六个诊断桶的题目分布（饼图/计数）——**这是定位问题的入口**
- 按 `route_sources` 的贡献度（哪条召回路在干活）

## 8. 计算示例（以 q001 为例）

题目（来自评测集）：
- Q：「本最佳实践覆盖哪些非SDN的老旧网络组网场景？」
- E（5 条）：`["HSRP+vPC/FEX/FabricPath组网", "MSTP+VRRP组网", "堆叠+Eth-Trunk组网", "SVF组网", "多级M-LAG组网"]`
- F（拆自 expected_answer，5 条事实）：`{HSRP+vPC/FEX/FabricPath, MSTP+VRRP/PVST+HSRP, 堆叠+Eth-Trunk, SVF, 多级M-LAG}`

假设召回 Top-K（K=10）后：
- chunk#0 命中 `HSRP+vPC/FEX/FabricPath组网`、`MSTP+VRRP组网`
- chunk#2 命中 `堆叠+Eth-Trunk组网`、`SVF组网`
- `多级M-LAG组网` 未命中
- Top-10 里有 4 个 chunk 相关，6 个无关

逐项：
- HitRate@K = 1
- Recall@K = 4/5 = **0.80**
- rank_first = 0 → MRR@K = 1/(0+1) = **1.00**
- NDCG@K：相关位 {0,2} → DCG = 1/log2(2) + 1/log2(4) = 1 + 0.5 = 1.5；IDCG = 1 + 1/log2(3) = 1 + 0.631 = 1.631 → **0.92**
- Precision@K = 4/10 = **0.40**（噪声率 0.60，偏高）
- ContextRecall = 4/5 = **0.80**

维度分：
- score_find = 0.80
- score_rank = 0.5·1.00 + 0.5·0.92 = 0.96
- score_quality = 0.4·0.40 + 0.6·0.80 = 0.64

综合分：
```
S_q = 0.40·0.80 + 0.25·0.96 + 0.35·0.64 = 0.32 + 0.24 + 0.224 = 0.784
```

诊断：`Recall=0.8≥0.5`、`rank_first=0≤3`、`ContextRecall=0.8≥0.8` → **PASS**；
但 `Precision=0.40` 触及 Noisy 临界，报表里应提示"召回偏噪，可调小 Top-K 或加 rerank"。

## 9. 评测集 Schema 扩展需求

当前评测集已有 `expected_evidence_contains`（= 证据包 E）。为支撑指标 6（事实可回答率），需新增：

```yaml
- id: q001
  # ... 现有字段 ...
  answer_facts:                        # 新增：答案事实包 F，每条一个原子事实
    - text: "支持 HSRP+vPC/FEX/FabricPath 组网"
      keywords: ["HSRP", "vPC", "FabricPath"]   # Tier1 关键词覆盖判定用
    - text: "支持 MSTP+VRRP / PVST+HSRP 组网"
      keywords: ["MSTP", "VRRP"]
    # ...
```

`keywords` 供 Tier1 确定性判定；`text` 供 Tier2 LLM 裁判。二者并存，可按需切换档位。

## 10. 对现有 runner.py 的改造清单

| 项 | 现状 | 改造 |
|---|---|---|

## 11. 一页速查

```
三包：  问题 Q   →   证据包 E（找得到）   +   答案事实包 F（答得出）

六指标： HitRate@K  Recall@K  MRR@K  NDCG@K  | Precision@K  ContextRecall
         └────── 证据包 E（定位） ──────┘    └ 噪声 ┘  └ 充分性(F) ┘

三维度： 召回 score_find(0.40) | 排序 score_rank(0.25) | 纯度+充分 score_quality(0.35)

单题分： S_q = 0.40·Recall + 0.25·(½MRR+½NDCG) + 0.35·(0.4·Prec + 0.6·CtxRecall)

PASS：   Recall≥0.5 且 rank_first≤3 且 ContextRecall≥0.8

诊断桶： 空召回 / 错召回 / 低排序 / 高噪声 / 不可答 / 健康

KB分：   Σ(w_d·S_q)/Σw_d ，难度权重 easy1 / medium1.5 / hard2
```

# 第二部分 · 【L0】知识资产层评测指标

> 目标：评「**知识本身**」的质量——本体 / 图谱 / 切块 / 嵌入。这是 L1 的上游，**L1 的「空召回 / 错召回 / 不可答」，根因常在这一层**。L0 的核心价值不是排名，而是**根因下钻**：告诉你该回去修哪道上游工序。

## 12. L0 输入物料与四个子层

### 12.1 输入物料

| 物料 | 记号 | 来源 | 角色 |
|---|---|---|---|
| 本体/Schema | `O` | ontology induction 产出（类、关系、is-a 层级） | 知识的「骨架」 |
| 三元组/图谱 | `T` | 抽取产出（实体–关系–实体） | 知识的「血肉」 |
| 切块 | `C` | parse/chunk 产出 | 喂给 L1 的最小检索单元 |
| 嵌入索引 | `V` | embedding 产出 | L1 检索的相似度空间 |
| 源语料 | `D` | 原始文档 | data-driven 评估基准 |
| 答案事实包 | `F` | **复用 L1 的 F**（§2） | 评切块完整性的标尺 |
| （可选）金标 | `O*/T*` | 人工/专家本体或三元组 | gold-standard 对照 |

L0 分四个**子层**，每子层产出一个 ∈[0,1] 的子层分；多数指标**无需金标**（结构检查 / 规则校验 / 复用 F），少数需金标的标注「金标」。

### 12.2 子层 O — 本体/Schema 质量（知识骨架）

| # | 指标 | 公式（单次） | 衡量什么 | 需金标? |
|---|---|---|---|---|
| O1 | **概念覆盖率** Coverage | `|O.类 ∩ 领域核心概念| / |领域核心概念|` | 该建模的概念建模了吗 | 金标，或从 `D` 抽高频术语 |
| O2 | **层级一致性** Hierarchy | `1 − (环路 + 矛盾 is-a 数) / is-a 总数` | 分类树有没有环 / 自相矛盾 | 否（结构检查） |
| O3 | **关系落地率** Grounding | `有 ≥1 实例支撑的关系类型 / 关系类型总数` | 有没有定义了却没人用的「空壳关系」 | 否 |
| O4 | **简洁性** Conciseness | `1 − 语义重复类对数 / 类总数` | 有没有近义重复的类（如「设备」vs「装置」） | 否（嵌入聚类） |

`score_ontology = 0.4·O1 + 0.2·O2 + 0.2·O3 + 0.2·O4`（覆盖率最重要，建模没覆盖到，下游整类问题无从谈起）。

### 12.3 子层 G — 图谱/三元组质量（知识血肉）

| # | 指标 | 公式 | 衡量什么 | 需金标? |
|---|---|---|---|---|
| G1 | **抽取准确率** Accuracy | 抽样三元组中「忠于源文」的比例 | 抽得对不对（不编造、不曲解） | 人工/LLM 抽样判 |
| G2 | **实体召回** Completeness | `|抽出实体 ∩ 金标实体| / |金标实体|` | 该抽的实体抽到了吗 | 金标 |
| G3 | **约束一致性** Consistency | `1 − 违反本体约束的三元组 / 三元组总数` | 类型不符 / 基数冲突 / 取值矛盾 | 否（规则校验） |
| G4 | **实体去重** Dedup | `1 − 重复实体节点对 / 实体总数` | 同一现实实体被拆成多个节点? | 否（消歧聚类） |
| G5 | **连通度** Connectivity | `1 − 孤立节点 / 节点总数` | 有没有挂不上图、检索不到的孤岛知识 | 否 |

`score_graph = 0.3·G1 + 0.25·G2 + 0.2·G3 + 0.15·G4 + 0.1·G5`（准确+召回是基本盘，权重最高）。

### 12.4 子层 C — 切块质量（直接喂 L1，最影响检索）

| # | 指标 | 公式 | 衡量什么 | 来源 |
|---|---|---|---|---|
| C1 | **事实完整性** FactIntegrity | `F 中能在「单个 chunk 内」被完整支撑的事实数 / |F|` | 关键事实有没有被切成两半 | **复用 F** |
| C2 | **尺寸健康** SizeHealth | 落在 `[min,max]` 字数区间的 chunk 比例 | 切太碎（丢上下文）/ 太大（夹噪声）? | 否 |
| C3 | **边界质量** Boundary | 在标题/语义边界切分的 chunk 比例 | 有没有切在句子中间 | 否 |

`score_chunk = 0.6·C1 + 0.2·C2 + 0.2·C3`（C1 是 L1「不可答」的直接病根，权重过半）。

> C1 是 L0↔L1 的关键桥：L1 的 ContextRecall 低（答不全），若 C1 也低，根因就锁定在「切块把事实割裂」，而非检索本身。

### 12.5 子层 V — 嵌入可检索性（索引空间质量）

| # | 指标 | 公式 | 衡量什么 | 来源 |
|---|---|---|---|---|
| V1 | **正负可分度** Separability | `mean(相关 chunk 相似度) − mean(随机 chunk 相似度)` | 相关的近、无关的远? | 复用 E/F 配对 |
| V2 | **邻域纯度** NeighborPurity | 每个 chunk 的 top-k 近邻中「同主题/同源」比例 | 索引空间里「相似」是不是真相似 | 主题标签或 source_ref |

`score_embed = 0.6·V1_norm + 0.4·V2`（V1 归一化到 [0,1]）。V1 低 = L1「错召回/低排序」的根因。

## 13. L0 知识资产健康分、诊断与 PASS

### 13.1 综合分

```
score_asset = w_o·score_ontology + w_g·score_graph + w_c·score_chunk + w_v·score_embed
默认权重：w_o=0.20, w_g=0.30, w_c=0.30, w_v=0.20
```

**权重依据**：切块（C）与嵌入（V）直接决定检索表现，合计 0.5；图谱（G）决定能召回的内容质量；本体（O）决定知识的覆盖上限。权重按场景可调。

### 13.2 诊断桶（核心 —— L0 桶 ↔ L1 桶 的因果对照）

L0 的真正价值在这张表：当 L1 某个诊断桶频发，回这里查对应的 L0 病根。

| L0 诊断桶 | 判定 | 病根 | **对应的 L1 症状** | 处置 |
|---|---|---|---|---|
| **源缺失** SourceGap | `G2` 低 | 源文档没这知识 / 没抽出来 | → L1「空召回 Empty」 | 补源文档、调抽取召回 |
| **切割割裂** Fragmented | `C1` 低 | 关键事实被切碎 | → L1「不可答 Unanswerable」 | 改 chunk 策略、加重叠 |
| **索引模糊** BlurredIndex | `V1` 低 | 相关/无关分不开 | → L1「错召回 Miss / 低排序 Buried」 | 换/微调 embedding、加 rerank |
| **图谱脏** DirtyGraph | `G3/G4` 低 | 冲突/重复实体 | → 检索到自相矛盾的内容 | 消歧去重、补约束校验 |
| **本体偏窄** NarrowOntology | `O1` 低 | 整类概念没建模 | → 整类问题系统性召不回 | 扩本体、补领域概念 |
| **健康** Healthy | 各子层达标 | — | — | — |

> 这就是「**越往下越是病根**」的落地：L1 的诊断桶告诉你「现象」，L0 的诊断桶告诉你「该回哪道工序修」，形成跨层根因闭环。

### 13.3 PASS 与聚合

- **资产级 PASS**：每子层分 ≥ 各自阈值（建议 `score_chunk≥0.8`、`score_graph≥0.7`、`V1` 超 margin 阈值、`O1≥0.8`）。
- **聚合**：按**文档**或**本体域**分组看 `score_asset`，定位是哪批文档 / 哪个领域的知识资产拖后腿——而不是只给一个全局总分。

### 13.4 L0 一页速查

```
四子层：  本体 O(骨架) | 图谱 G(血肉) | 切块 C(检索单元) | 嵌入 V(索引空间)

子层分：  O: 覆盖O1/层级O2/落地O3/简洁O4
          G: 准确G1/召回G2/一致G3/去重G4/连通G5
          C: 事实完整C1 / 尺寸C2 / 边界C3      （C1 复用 F）
          V: 可分度V1 / 邻域纯度V2

资产分：  0.2·O + 0.3·G + 0.3·C + 0.2·V

根因桶：  源缺失→L1空召回 | 切割割裂→L1不可答 | 索引模糊→L1错召回/低排序
          图谱脏→检索到矛盾 | 本体偏窄→整类召不回
```

# 第三部分 · 【L4】业务价值层评测指标（对照组增量）

> 目标：用「**对照组**」量化知识库的**增量价值**，回答那个终极问题——「**不用库，通用大模型自己不就答了？这库值不值得建？**」。L1/L0 评的是「过程好不好」，L4 评的是「最终到底有没有创造价值」。

## 14. L4 输入物料与三路对照

### 14.1 三路对照（核心设计）

同一批题、同一裁判、同一答案格式，**只换「给不给库」这一个变量**：

| 路 | 配置 | 实现（复用 `agent_runner`，只改挂载的工具） | 角色 |
|---|---|---|---|
| **A 闭卷** | 通用 LLM，不给任何检索 | `claude -p`，不挂 MCP | 基线（学生没发手册） |
| **B 联网** | 通用 LLM + 公网搜索 | `claude -p` + web search 工具 | 强对照（可选）：证明库强过「随便搜搜」 |
| **C 用库** | 通用 LLM + 知识库 MCP | `claude -p` + `search_knowledge`（= L2/L3 采集的 agent trace） | 被测（学生发了手册） |

> 三路共用 `agent_runner`，差别仅在 `--mcp-config` / `--allowedTools`，工程成本极低。

### 14.2 基础：答案质量分 `Score_x`

对每一路答案，用**同一个裁判**对照答案事实包 F 打分（复用 runtime-eval 的 `/judge`）：

```
Score_x = 该路答案命中的事实数 / |F|         （Tier1 关键词覆盖，零成本）
       或 = judge(answer_x, F) 的综合分        （Tier2 LLM 裁判，更准）
```

得到三个分：`Score_A`（闭卷）、`Score_B`（联网）、`Score_C`（用库）。

> **关键依赖**：L4 全部建立在裁判公平之上。三路必须同一 prompt、同一模型；用 pairwise 比较时**正反各跑一次去位置偏见**。裁判本身需先用人工金标校准一致率（详见分层框架文档的「判官校准」专题）。

## 15. L4 增量指标、诊断与价值分

### 15.1 增量指标（单题 + 聚合）

| # | 指标 | 公式 | 衡量什么 |
|---|---|---|---|
| 1 | **绝对增量** Uplift_abs | `Score_C − Score_A` | 用库后净提升多少分 |
| 2 | **相对增量** Uplift_rel | `(Score_C − Score_A) / max(Score_A, ε)` | 在原有基础上提升了百分之几 |
| 3 | **对联网增量** Uplift_web | `Score_C − Score_B` | 比「随便上网搜」强多少（**护城河**） |
| 4 | **胜率** WinRate | C 优于 A 的题占比（pairwise，去位置偏见） | 比均值更稳健的「赢面」 |
| 5 | **负增量率** RegressionRate | `Score_C < Score_A − δ` 的题占比 | **库帮倒忙的比例（风控线）** |
| 6 | **不可替代率** Exclusivity | `Score_A < τ_low 且 Score_C ≥ τ_high` 的题占比 | 库的「护城河题」占比 |

### 15.2 单题诊断桶（C vs A）

| 桶 | 条件 | 含义 | 启示 |
|---|---|---|---|
| **不可替代** | A 低、C 高 | 库的独有价值 | 库的**核心战场**，多积累这类题 |
| **锦上添花** | A 中/高、C 更高 | 库正向提升 | 健康 |
| **平局（通用知识）** | A 高、C≈A | 通用模型本就会 | 正常，**不代表库没用** |
| **帮倒忙（负增量）** | A 高、C 低 | 召回噪声把答案带歪了 | ←重点查，常是 L0/L1 问题 |
| **双输** | A 低、C 低 | 库也没救回来 | 根因在 L0 源缺失 / L-1 |

> 「帮倒忙」「双输」两桶恰好把问题**甩回 L0/L1 做根因下钻**——三层闭环：L4 发现「没创造价值」，L1 看「检索哪步崩」，L0 看「知识哪里烂」。

### 15.3 KB 价值分与 headline

```
难度加权净增量 = Σ_q w_d·(Score_C − Score_A) / Σ_q w_d      （hard 题增量权重更高）
加权胜率       = Σ_q w_d·[C 胜] / Σ_q w_d
价值 PASS（库值得建）⟺ 净增量 ≥ 阈值 且 负增量率 ≤ 阈值（建议 5%）
```

**headline 四件套**（一句话讲完整故事）：`净增量 / 胜率 / 负增量率 / 不可替代率`。

### 15.4 分层呈现（洞察核心，务必分层）

**绝不能只看总分**——通用常识题（「SDN 是什么」）通用模型本就会答，增量≈0 是正常的；私有领域题（「本最佳实践覆盖哪些非 SDN 老旧组网场景」）通用模型根本不知道，增量最大。必须按 `question_type / difficulty / 领域` 分组看增量，否则总分会被通用题稀释，误判「库没用」。**库的卖点藏在 hard 题和私有题的增量里。**

### 15.5 L4 一页速查

```
三路对照： A 闭卷(基线) | B 联网(强对照) | C 用库(被测)   —— 同题同判官，只换给不给库

答案分：   Score_x = 命中事实数 / |F|   （复用 L1 的 F）

六增量：   绝对Uplift | 相对Uplift% | 对联网增量 | 胜率 | 负增量率 | 不可替代率

诊断桶：   不可替代(A低C高) | 锦上添花 | 平局(通用知识) | 帮倒忙(负增量) | 双输

价值分：   Σ(w_d·(Score_C−Score_A))/Σw_d ，PASS ⟺ 净增量达标 且 负增量率≤5%

铁律：     必须分题型/难度看增量，总分会被通用题稀释
```
