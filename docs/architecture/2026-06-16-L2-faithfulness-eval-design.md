# L2 答案对照层 · 多模型 × 黄金答案评测设计

> 状态：方案（已定稿 → 转实现计划）
> 日期：2026-06-16
> 适用：runtime_eval（eval-web SPA + eval-api + eval-llm）
> 关联：[分层评估框架设计](2026-06-04-layered-eval-framework-design.md)（本文落实其中的「L2 生成层」）、L4 增量价值层（uplift，已实现）

---

## 0. 一句话

把"证据包"焊死不动，让**花名册里的多个 LLM**各基于它整合一版最终答案，再用**同一个固定裁判**把每版答案跟**黄金标注的最终答案**比，打 **覆盖度 + 准确度 + 矛盾** 三个分（综合分 F1 排序），最后出一张模型排行榜 + 逐题下钻。

**打比方**：同一份《案情卷宗》（证据包）发给几个律师（参赛 LLM）各写一份**结案陈词**（模型整合的最终答案 A）；我们手里有一份**标杆陈词**（黄金最终答案 G）。一个固定法官（裁判模型）只比 A 跟 G 差多少——① G 里该说的要点 A 说全没（**覆盖度**，防漏）；② A 写的内容有几句是 G 认可的、几句是多余跑题（**准确度**，防掺水）；③ A 有没有跟 G 直接说反的（**矛盾**，防硬伤）。换律师不换法官，比的才是律师本事。

**关键**：打分锚点是**黄金最终答案 G**，不是证据包。证据包只是喂给 agent 的固定输入（决定大家起跑线一样），不是标尺。

## 1. 这层在分层框架里的位置

| 层 | 评什么 | 现状 |
|---|---|---|
| L4 价值层 | 用库 vs 不用库强多少 | ✅ 已实现（uplift） |
| **L2 答案对照层** | **固定证据下，各模型整合的答案 vs 黄金最终答案，差多少** | ❌ **本设计** |
| L1 检索层 | 召回找得到/排得准/够答全 | ✅ 已实现（retrieval_metrics） |

**与 L1/L4 的边界**：
- L1 测"捞得对不对"，L2 把捞到的东西**焊死**当输入，只测"拿着同一份料、哪个模型整合出的答案最接近标准答案" —— 隔离掉检索变量，单独考"生成"这道工序，且**横向比模型**。
- L4 测"用库比不用库强多少"（端到端价值），L2 测"同样用库，换不同 LLM，谁整合得最好"（模型选型）。一个测要不要用库、一个测用哪个模型。

## 2. 核心数据流（每道题）

```
证据包 = L1 检索回来的那份片段（RetrievalSet.for_case(case_id)，固定不换）
黄金 G  = 用例里的 expected_answer（标注的最终答案）+ key_points（评分要点）
对花名册里每个模型 m：
   答案_m  = m 基于(问题 + 证据包) 整合一版最终答案
   对照_m  = 固定裁判把「答案_m」跟「黄金 G」比，一次出三组判定：
              · 覆盖：G 的要点命中/遗漏清单   → 覆盖度
              · 准确：答案_m 的论断里 G 认可/多余清单 → 准确度
              · 矛盾：答案_m 里跟 G 说反的清单     → 矛盾(硬伤)
   综合分_m = F1(覆盖度, 准确度)
全套题跑完 → 每个模型聚合：平均覆盖/准确/综合分 + 硬伤数 / token / 时长 → 排行榜（综合分排序，可逐题下钻）
```

**三个指标的精确定义**（全部锚定黄金最终答案 G）：

- **覆盖度（coverage / recall）**：G 里的关键信息点（`key_points`），答案命中了几个。分数 = 命中点数 / 要点总数。防"漏"。
- **准确度（correctness / precision）**：把答案拆成若干论断，逐条判"G 支不支持"；分数 = G 支持的论断数 / 答案论断总数。G 之外的（多余/跑题）拉低此分。防"掺水"。
- **矛盾（contradiction）**：答案里跟 G **直接说反**的论断（不是没提，是说错）。单列清单 + 有无硬伤标志——比"漏"更严重，需高亮提示。

**综合分（F1）**：`F1 = 2·覆盖度·准确度 / (覆盖度 + 准确度)`，兼顾"全"与"准"，排行榜主排序用此分。

三个指标**正交**：覆盖高准确低 = "点都提了但掺了多余/错的"；覆盖低准确高 = "说的都对但答得不全"；矛盾单独看 = "有没有硬伤"。分开看才有诊断价值。

> **不评什么（已剔除）**：早期方案曾设"忠实度（答案 vs 证据包，判有没有超出证据瞎编）"。该指标锚点是输入证据、不是黄金答案，与本层目标（A vs G）错位，**已剔除**；证据包只作 agent 的输入，不进打分。

## 3. 模型花名册（可插拔，首发少接）

### 3.1 花名册结构
一张配置化的"花名册"，每个条目描述一个**参赛模型**：
```
RosterEntry:
  id:        稳定标识（如 "claude-sonnet"）
  label:     显示名（如 "Claude Sonnet"）
  channel:   调用通道，枚举：claude_cli | llm_service | anthropic
  model:     该通道下的具体模型名（如 claude_cli 的 --model 档位）
  enabled:   是否参赛
```
花名册存为配置（环境变量 / 配置文件），eval-api 启动时加载；前端可读取展示"本次有哪些选手参赛"。

### 3.2 调用通道改造（关键 plumbing）
现状：`LLMClient.run_agent(question, system, route)` 只认 `route`，模型由 provider 的全局配置（`agent_model` 等）决定，**不能按请求点名换模型**。

改造：给作答链路加一个**按请求覆盖模型**的入口——`run_agent(..., model=<roster.model>)`，由 eval-llm 侧据此选具体模型档位执行单题作答（claude_cli 的 `--model`）。这是"可插拔"的落点：新增一个 vendor 只需实现一个 channel + 在花名册加一行。

### 3.3 首发接入范围
- **首发内置（确定能白嫖）**：Claude 的 `haiku` / `sonnet` / `opus` 三档，走 `claude_cli --model`，复用已登录订阅，不花 API 钱。
- **serving 不进花名册（已定）**：serving（agent_serving_java）**只做检索、不写答案**；写答案那一步是 agent 干的。所以 serving 当不了"答题选手"，**不进花名册**；它检索回来的片段仍是 L1/L2 的证据包来源（`RetrievalSet.for_case` 的上游）。
- **其余厂商（GPT / 通义 / DeepSeek 等）**：留 channel 接口，以后按需加，不在首发。

## 4. 三个已定决策

1. **裁判固定**：覆盖/准确/矛盾都用 config 里那个**固定 judge 模型**给所有参赛模型打分，只换选手不换裁判 —— 同 L4「同题同判官」原则，否则比较不公平。
2. **复用 L4 的 SSE 进度条**：多模型 × 全题 = 大量 LLM 调用，必然慢。套用刚落地的流式进度（`iter_value_uplift` 同款）：每个模型一段「作答 → 对照判」，逐题推 `case_start/case_done`，前端进度行实时刷 `⟳ sonnet·作答 第3/8题…`。
3. **门禁**：L2 依赖证据包，**没跑过 L1 检索的题不能跑 L2**。进入前检查每题是否有 `RetrievalSet` 片段；缺的提示"先去补检索"，不静默跳过。

## 5. 落库与缓存

- 新增一层快照：`RunSummary(layer="answer_match", kind="multi_model", run_id="ans_<sid>")`，`metrics` 含：每个模型的聚合分、排行榜（综合分排序）、逐题明细（答案 + 覆盖/准确/矛盾 + 命中/遗漏/多余/矛盾清单）。
- 每个模型的原始答案 + 对照判结果留底，支持前端逐题下钻。
- **缓存（对接此前 A 期诉求）**：缓存键 = `(证据包指纹 + 模型 id + 题目内容指纹)`。三者没变 → 命中直接复用，不重跑该(模型,题)。证据包或题目一变 → 该项失效需重跑。

## 6. 后端组件

- **eval-llm**：新增**答案对照裁判** prompt + 端点（`POST /judge-answer`，入参 `question + answer + expected_answer + key_points`，**一次调用**出参 `covered_points[] / missed_points[]`（覆盖）+ `correct_claims[] / extra_claims[]`（准确）+ `contradictions[]`（矛盾）+ `rationale`）；作答端点 `/run-agent` 支持按请求 `model` 覆盖。
- **eval-api**：
  - `orchestrator.iter_answer_match(...)`：仿 `iter_value_uplift` 的生成器，按"模型 × (作答/对照判)"逐题 yield 进度，跑完落 `RunSummary`。
  - `run_answer_match(...)`：drain 生成器取回快照（阻塞版，给非流式调用/测试用）。
  - 端点：`GET /api/v1/suites/{sid}/answer-match:run/stream`（SSE）、`GET /api/v1/suites/{sid}/answer-match`（读最近快照）、`GET /api/v1/eval-roster`（读花名册）。
- **复用**：`RetrievalSet.for_case`（证据包）、`run_agent route="closed_book"`（把证据揉进提示、不再检索的作答通道）。

## 7. 前端

- 评测台新增 **L2 卡片**（与 L4 uplift 卡片并列）：
  - 顶部"参赛选手"= 花名册里 enabled 的模型；一个「跑答案对照」按钮 + SSE 进度行（复用 L4 进度条样式）。
  - 主体 = **排行榜表格**：`模型 / 综合分 / 覆盖度 / 准确度 / 硬伤数 / token / 时长`，按综合分排序。
  - 点某行展开 = 该模型逐题：题目 / 它的答案 / 覆盖（+遗漏点）/ 准确（+多余点）/ 矛盾（硬伤高亮）。
- 静态资源版本号照例 bump，避免浏览器缓存旧 JS。

## 8. 测试

- **orchestrator**：`iter_answer_match` 用 duck-typed 多模型 fake，断言事件序列（每个模型一段作答/对照判）、聚合排行榜（综合分排序）、落库 `ans_<sid>`；`run_answer_match` drain 后取回快照。
- **答案对照裁判**：给一段"漏了要点 + 含与黄金矛盾断言"的答案，断言 `missed_points` 非空、`contradictions` 非空、覆盖度/准确度下降。
- **门禁**：未检索的题跑 L2 → 清晰报错/提示，不静默。
- **缓存**：同(证据包+模型+题)二次跑命中、不重复调模型；题目变 → 失效重跑。
- **SPA 断言**：`answer-match:run/stream` / `eval-roster` 接线存在；旧断言回归。
- 全量 `pytest` 绿灯。

## 9. 阶段拆分（供写实现计划参考）

1. **花名册 + 按请求换模型**：RosterEntry 配置加载 + `/run-agent` 支持 model 覆盖 + `GET /eval-roster`。（地基，先验证 claude_cli 换档真生效）
2. **答案对照裁判**：eval-llm `/judge-answer` prompt + 端点（一次出覆盖/准确/矛盾）+ 单测。
3. **编排 + SSE**：`iter_answer_match` / `run_answer_match` / `answer-match:run/stream` / `answer-match` 读取端点 + 落库 + 门禁。
4. **缓存**：按 `(证据包+模型+题)` 指纹命中复用。
5. **前端**：L2 卡片 + 排行榜（综合分排序）+ 逐题下钻 + SSE 进度（复用 L4 组件）。

## 10. 待确认 / 风险

- ~~serving 是否算答题模型~~ —— **已定：serving 只检索不作答，不进花名册**（见 §3.3）。
- ~~打分锚点是证据还是黄金答案~~ —— **已定：只比黄金最终答案 G，综合分 F1 排序**（见 §2）。
- **claude_cli 多档真实可用性**：`--model haiku|sonnet|opus` 在订阅下是否都可调、是否额外耗额度，写代码第一步先用真实命令验证（同 L4 风险栏的"先验证再编排"原则）。
- **成本/时长**：模型数 × 题数 × 2 次 LLM（作答 + 一次对照判）。先小批量试跑，靠缓存 + SSE 进度缓解体感。
- **对照判的稳定性**：论断切分 + 准确/矛盾判定对 prompt 敏感，先定简单版（整段判 + 列各清单）再迭代到逐论断。
